1 What WordPress needs to run

WordPress is PHP code that stores its content in a database. Almost everything in this lesson follows from that: the code is files you can keep in git, and the content is rows in a database that git does not see.

The official requirements page lists what a host should support. As read on 27 Oct 2026 it recommends: PHP version 8.3 or greater; MariaDB 10.11 or greater, or MySQL 8.0 or greater; HTTPS support; and Apache or Nginx as the web server. These numbers move with each release, so treat them as a snapshot and check the page when you pick a host.

THE CODE SIDE (FILES)
WordPress core, your theme, your plugins and wp-config.php. Core and plugins arrive through updates; the theme and your own plugins are yours and belong in git. Uploaded media also sits on disk, but it is content and does not belong in git (section 3).
THE CONTENT SIDE (DATABASE)
Posts, pages, menus, settings, plugin options and users live in the database. Anything an editor changes in wp-admin changes a row, not a file. That is why a deploy of your git repository never carries content with it.

The settings that tie the two together are in wp-config.php (database name, user, host). That file differs per environment, so it is normally kept out of the shared code or generated per server.

2 Choosing a kind of hosting

Hosting for WordPress falls on a spectrum. At one end is general hosting: you get a server or an account and a control panel, and you manage WordPress on it. At the other is managed WordPress hosting: the provider runs the stack for WordPress specifically and often adds backups, staging and update tooling. This is a trade between control and convenience, not a ranking, and the features vary by provider, so the answer is a set of questions to ask rather than a product to name.     3 Code in git, content in the database

    Staging is a second copy of the site where you can try changes safely. The difficulty is that a WordPress site has two kinds of state that live in different places and should move in different directions. Code (theme files, your plugin code) is written on your machine, kept in git and flows towards production. Content (posts, settings, uploads) is written by editors on production and, when you need a realistic copy, flows back down to staging and local. Push the wrong thing the wrong way and you either lose editors’ work or break the site. Choose a kind of change and see both directions.     5 Moving a database: URLs and search-replace

    When you copy a database from one environment to another, WordPress still contains the old site address in many places. The migration guide says to export the database, move it, then update the WordPress Address and Site Address and fix remaining references. A plain text replace on a SQL dump is risky, because WordPress stores some values as PHP serialized strings that record each value’s length. WP-CLI’s search-replace is built to handle serialized data, and the guide says never to change the guid column. The simulator below uses a made-up row to show why.

    wp db export before-move.sql # ... copy the file, import it on the new environment (wp db import) ... wp search-replace 'http://old.test' 'https://new.example' --skip-columns=guid --dry-run wp search-replace 'http://old.test' 'https://new.example' --skip-columns=guid

    The serialized row here is a small invented example, and the length check assumes plain ASCII characters. Transients can keep old addresses too; the guide notes they are safe to delete because WordPress recreates them. After the move, check menus, widgets, plugin settings and template files for hard-coded old URLs.

    6 Update day, in the right order

      8 Domains, DNS and SSL at cut-over

      A domain name points at a server through DNS records. Visitors do not ask the authoritative DNS every time: resolvers cache the answer for the record’s TTL (time to live). So when you point the name at the new server, some visitors keep reaching the old one until their cached answer expires. The new server also needs an HTTPS certificate for the name, or browsers warn. How and when a certificate is issued depends on the host. This part is background knowledge, not something the WordPress documentation covers (its migration guide does not cover DNS). Move the slider; the split is a simplified model that assumes caches were filled evenly across the TTL.

      A plan that avoids surprises. (My synthesis.) Lower the TTL a day or two before cut-over, get the certificate and the final content sync ready, freeze editing for the sync, change the record, then watch both servers until traffic has moved. Keep the old server untouched for a while so you can switch back.

      ✦ Takeaways & sources

      • WordPress needs PHP, a MySQL-compatible database and HTTPS support; check the official requirements page for current versions.
      • Hosting is a trade: managed hosting adds convenience, general hosting adds control. Ask every host the same questions about staging, backups, WP-CLI or SSH and git deploys.
      • The hard part is the database: code flows up from git, content flows down from production, and mixing the two is how work gets lost.
      • Use a serialization-aware tool such as WP-CLI search-replace when changing addresses, and leave the guid column alone.
      • Update in order: verified backup, staging, test, production, verify, then decide whether to roll back.
      • Test your backup restore before you need it, and write down how long it took.
      • DNS moves at the speed of its caches; prepare the certificate and the TTL before cut-over.
