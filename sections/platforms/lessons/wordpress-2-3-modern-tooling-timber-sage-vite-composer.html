Modern WordPress Tooling: Timber, Sage, Vite and Composer

What a "professional" WordPress stack adds on top of a classic theme: a templating layer, a build step for assets, dependency management, and automated checks, plus what each one costs the next person who inherits the project.

1 What problem each tool solves

A classic theme (lessons 1.2 and 2.1) needs nothing but PHP, HTML and CSS files in a folder. That is its strength. Modern tooling answers four specific complaints that show up as a project grows.

Think of each tool as an answer to one question, and notice that you can adopt them separately:

  • PHP and HTML are tangled in templates. Timber keeps the PHP in one file that gathers data, and puts the markup in a Twig template. Its docs describe it as separating logic from markup, and it can be adopted gradually, replacing one part of a theme at a time.
  • The front-end has outgrown a hand-written stylesheet. Sage, from the Roots team, is a starter theme built on Laravel's Blade templates, Tailwind CSS and block editor support. Its installation uses Composer and an npm build.
  • Assets need compiling. A bundler (Vite, or webpack through @wordpress/scripts) turns modern source files into the files the browser loads.
  • Dependencies are copied by hand. Composer declares libraries in a file and installs the exact versions for everyone. The Roots project Bedrock goes further and manages WordPress core and plugins with Composer too.

Lesson 2.1 covered the Loop and escaping inside classic templates; this lesson assumes that and looks at what wraps around it. If you know a theme with no build step, such as a Shopify theme, the classic WordPress theme is the same situation: files you edit are files that run.

    3 From source assets to enqueued files

    A bundler takes your source JavaScript and CSS and writes the files the browser will load. The WordPress side then has to put the right tags in the page. The route differs between development, where a server rebuilds as you type, and production, where you build once. Choose a tool and a mode and step through it.

    What the sources say. For Vite, the backend integration guide describes production as: run the build, read the generated manifest to find the hashed file names, then output the stylesheet links followed by the script tag. In development, the page instead loads the @vite/client script and your entry file from the dev server. For @wordpress/scripts, build makes one production build and start runs an incremental build that rebuilds on change; the default output folder is build/, and it uses webpack. Sage's install page warns that the site will not load without built assets and shows a missing Vite manifest error. Which tool is right depends on what you are building: @wordpress/scripts is aimed at blocks and plugins, Sage uses Vite for a whole theme.

    4 Composer and the Bedrock layout

    Composer reads a composer.json that lists what the project requires. Running composer update resolves the versions, writes the exact ones into composer.lock, and installs into vendor/. Running composer install instead installs exactly what the lock file says, so everyone gets the same code. The Composer docs advise committing the lock file and keeping vendor/ out of git.     The package name and "resolution" numbers above are illustrative; real lock files record real version numbers. Your own code loads libraries through the autoloader that Composer generates, vendor/autoload.php, and PSR-4 autoloading maps a namespace to a source folder so classes load without manual require lines.

    Bedrock applies the same idea to the whole site. According to the Roots page, it keeps only your own code, configuration and dependency list in git; WordPress core, plugins and themes are installed by Composer; the public document root is a web/ folder; and secrets such as database credentials live in a .env file outside the repository.       5 Linting, formatting and a pull request gate

      Tooling is also how a team agrees on quality without arguing in review. @wordpress/scripts bundles several checks as commands: lint-js (ESLint for JavaScript and TypeScript), lint-style (stylelint for CSS and Sass), lint-pkg-json for package.json, format for formatting, and build. A continuous integration (CI) service can run the ones you choose on every pull request. Turn checks on and see which of these seeded mistakes would be stopped before merge.

      Which check catches which mistake follows from what each command is described to do. The mistakes are my own examples. "Your own tests" means tests you wrote, such as PHP unit tests; none ships with this lesson, and running PHP lint or coding-standard tools is a further option this lesson did not research.

          ✦ Takeaways & sources

          • Each tool answers one problem: Timber for tangled templates, a bundler for assets, Composer for dependencies, linters and CI for agreed quality.
          • Timber keeps PHP that gathers data (Timber::context(), Timber::render()) apart from Twig markup, and can be adopted gradually.
          • Sage brings Blade, Tailwind and Vite; its install uses Composer and an npm build, and the site will not load without built assets.
          • Dev and production differ: a dev server during development, a build plus manifest lookup in production.
          • Composer: commit composer.lock, install from it, keep vendor/ out of git; Bedrock extends this to core and plugins.
          • It pays off on long-lived, multi-developer projects, and costs you when the client's next developer expects a classic theme.
