Custom Post Types, Taxonomies and Fields

How to model your own kind of content in WordPress: a post type for the thing, taxonomies for grouping it, and fields for its details, with the choice between native post meta and a field plugin such as ACF.

1 Model the content first

Before any code, decide what the things on the site are. A case study is not a blog post: it has a client, an industry, a results figure and a gallery. WordPress lets you describe that once and then gives editors a proper screen for it.

WordPress ships with five default post types: post, page, attachment, revision and nav menu items. Lesson 1.1 had a widget that sorted site content into the right type; this lesson is how you add a type of your own. Three tools make up the model: a post type for the thing itself, taxonomies to group things (by industry, by service), and fields (post meta, native or through a plugin) for its individual details.

One decision comes before all three: where the registration code lives. The handbook recommends registering post types in a plugin rather than a theme, so the content stays intact if the theme changes. Switch the theme below and see what happens to the editor's menu.

2 register_post_type, argument by argument

You register a type by calling register_post_type() on the init hook (lesson 1.1 covered hooks). It takes an identifier and an array of arguments. The identifier is at most 20 characters (it has to fit a database column), may hold only lowercase letters, numbers, dashes and underscores, should carry a prefix that identifies your plugin, theme or site, and must not begin with wp_, which core reserves. Everything about the new screen comes from the arguments, and most of them default to off. Change them below.

What each argument does, per the register_post_type() reference: public sets the defaults for several visibility options and is off by default; has_archive turns on an archive page (off by default); supports lists the core features and defaults to title and editor; show_in_rest exposes the type to the REST API and is required for the block editor; rewrite controls the permalink and its slug defaults to the identifier; menu_icon takes a Dashicons class, an image URL or a data URI. A slug clash can be fixed later by changing the slug, but an identifier clash cannot be fixed without disabling one of the two types, which is why a prefix matters.

After changing URLs, rewrite rules need flushing. The reference says a plugin should flush rewrite rules on activation (and deactivation) after registering, and a theme should do it on the after_switch_theme hook. If new URLs 404, this is the usual cause; saving the Permalinks settings screen is the quick manual fix (background knowledge, not stated on that page).

3 Taxonomies: flat or hierarchical

A taxonomy groups content. You register one with register_taxonomy(), also on init, giving an identifier, the post type or types it applies to, and arguments. The one argument that changes the model most is hierarchical. With true it behaves like categories: terms have parents and children, and the edit screen shows a checkbox list. With false (the default) it behaves like tags: a flat list, typed in as free text. WordPress also builds a term archive for each term. Toggle it and watch the edit screen change.

From the register_taxonomy() reference: show_admin_column adds a column for the taxonomy on the list screens, show_in_rest makes it available to the block editor, and the name must be 32 characters or fewer. The docs also warn against names that collide with reserved query terms such as category, tag and post_type. Helper functions you will meet in templates include the_terms() and wp_tag_cloud().

5 Post meta, hands on

Post meta is data attached to one post as a key and a value. Four functions cover it: add_post_meta( $post_id, $key, $value, $unique ), update_post_meta() (which creates the key if it is missing), delete_post_meta() and get_post_meta(). The detail that surprises people is that a key can hold several values unless you pass the unique flag, and that the third argument of get_post_meta() decides whether you get one value or a list. 6 ACF and flexible content

Native meta works, but the editor sees only a plain key and value box unless you build your own meta box. A field plugin supplies the interface. Advanced Custom Fields (ACF) is the common one: you define fields in its settings, editors get proper inputs (image pickers, selects, repeaters), and in a template you read a value with get_field( 'name' ). By default it reads from the current post; a second argument can target another post, and prefixes such as user_2 or category_3 target other objects. With formatting on, some fields return processed data, such as an image array instead of an ID. The ACF docs say you still escape what you print, for example with wp_kses_post() (lesson 2.1).

The field type worth understanding is Flexible Content, listed in ACF's docs as a PRO feature. Editors stack layouts (a hero, a text block, an image, a quote) in any order, and your template loops over them with have_rows() and the_row(), branching on get_row_layout() and reading values with get_sub_field(). 8 Choosing, and changing your mind

For each piece of data, which tool fits? A rough rule, my own synthesis rather than an official one: if people will browse or filter by a shared value, it is a taxonomy; if it is a one-off detail of a single post, it is a field, native meta when a developer manages it and a field plugin when editors need a good interface or reorderable layouts.

Changing the model later is where the cost shows up. Renaming a post type identifier, or moving a value from a field to a taxonomy, means existing rows must be migrated, usually with a script, and URLs may change so redirects are needed. None of that is hard, but it is much cheaper to think about before 400 entries exist. This is why the plan says good content modelling saves more time than any theme trick. If you have met Shopify metaobjects, the idea is the same: a defined structure for content that does not fit a product or a page.

✦ Takeaways & sources

  • Model first: a post type for the thing, taxonomies for shared grouping, fields for per-post details.
  • Register on init, in a plugin so content survives a theme change; prefix identifiers, keep them to 20 characters, avoid wp_.
  • Most arguments default to off: set public, has_archive and show_in_rest deliberately, and flush rewrite rules after changing URLs.
  • Taxonomies: hierarchical gives category-style trees; otherwise tag-style lists.
  • Post meta: one key can hold many values; get_post_meta() with true returns a single value; sanitise on save, escape on output.
  • ACF gives editors a real interface; get_field() reads values and Flexible Content (PRO) is a loop with one template branch per layout.
