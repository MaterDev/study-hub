1 A template is PHP wrapped around HTML

A classic theme template is an ordinary HTML file with PHP sprinkled in. The HTML is your markup. The PHP asks WordPress for the content and prints it. Lesson 1.2 showed which template file WordPress picks; this lesson is about what is inside that file.

The shape of almost every template is the same: load the header, loop over the posts that the main query found, print each one, load the footer. The loop is the part to understand properly, because every other template idea hangs off it.

2 The Loop, step by step

Before your template runs, WordPress has already worked out which posts the page needs and run the main query. The Loop is how you walk through those results. have_posts() asks "are there more posts to show?". the_post() moves to the next one and makes it the current post, so that template tags like the_title() know which post to talk about. Step through it, then try the case where the query finds nothing.

3 Template tags: print or return

Inside the Loop, template tags are the functions that print details of the current post: its title, its content, its excerpt, its featured image, its author and date. Most come in two flavours. The the_ version prints the value straight onto the page. The get_the_ version returns it so you can use it in your own PHP first (for example, to put it in an attribute). The pair idea is general WordPress convention; this lesson's sources list the printing tags. Pick a post and a tag.

4 Your own query, and putting things back

Sometimes a template needs a second list, such as "three related posts" under an article. You create that with new WP_Query() and give it arguments (post type, how many, which category) and loop over it with its own have_posts() and the_post(). The catch is that the_post() also changes the global current post. After your loop, the page is still "looking at" the last related post. wp_reset_postdata() restores the global current post to the main query's. 5 Changing the main query safely

To change what the main query fetches (say, 24 products per page on the products archive), do not run a second query and do not call query_posts(). Hook pre_get_posts. It runs after the query object exists but before it runs, and it passes the query in by reference, so what you change is what runs. The danger is that it fires for every query on the site, so you must check you are touching the right one: not an admin screen (! is_admin()), only the main query ($query->is_main_query()), and only the archive you mean ($query->is_post_type_archive( 'product' )). Switch the guards off one at a time and see who else gets changed. The yes and no values below are illustrative.

One more rule from the reference: because pre_get_posts runs before the query is fully set up, some conditional tags such as is_front_page() do not work inside it; use the query object's own methods instead.

6 Escaping: protect the output

Anything that was typed by a person (a post title, a custom field, a search term) can contain markup. If you print it raw, a visitor's browser may run it. The rule is escape late: escape at the moment you output, using the function that fits where the value lands. esc_html() for text inside an element, esc_attr() for an attribute value, esc_url() for any URL, esc_textarea() inside a textarea, and wp_kses_post() when you want to keep the HTML allowed in post content. There are also combined translate-and-escape helpers such as esc_html__(). Type something nasty and compare.

7 Debugging: seeing what went wrong

When a template misbehaves, WordPress can tell you why, if you ask. Three constants in wp-config.php, placed above the "stop editing" comment, control it: WP_DEBUG turns debug mode on, WP_DEBUG_LOG writes errors to wp-content/debug.log, and WP_DEBUG_DISPLAY decides whether errors print into the page. The log and display switches only do anything when WP_DEBUG is on. Write the values as real true or false, not in quotes: a quoted false is a string, and a string counts as true.

Keep debugging off on live sites. These switches are meant for local and staging copies. A common safe setup elsewhere is debug on, display off and log on, which records errors without showing them to visitors. Back up or use a staging copy before changing anything.

✦ Takeaways & sources

  • A classic template is PHP around HTML: header, the Loop, footer.
  • The Loop: have_posts() asks, the_post() advances and sets the current post, template tags print it, and an else branch handles "nothing found".
  • Template tags print or return: the the_ forms print; the get_the_ forms return.
  • Secondary queries need a reset: call wp_reset_postdata() after your own loop.
  • Change the main query with pre_get_posts, guarded by admin, main-query and archive checks.
  • Escape late and match the function to the place: html, attribute, url, textarea, or kses for allowed markup.
  • Debug in development only, and keep error display off in production.
