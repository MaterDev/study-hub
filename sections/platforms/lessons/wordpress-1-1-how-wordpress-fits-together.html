1 One request, start to finish

WordPress is a PHP program that runs on every page request. It boots, loads your plugins and theme, works out which content was asked for, picks a template from your theme, and prints HTML. Along the way it fires hooks, named moments where other code (yours) can step in. Learning the order of those moments is most of what "knowing WordPress" means for a developer.

Press Run a request to watch the main hooks fire in order, or click any hook to see what it is for. This is a simplified path through WordPress's action sequence; the Action Reference lists the full order and calls it approximate.

2 Hooks: actions and filters

Hooks let one piece of code extend or change another at predefined points. They are how plugins and themes plug into core, and core uses them heavily too. There are two kinds, and the difference is the single most useful thing to get straight:

Action: "do something now"

Runs at a specific point to perform a task such as printing output or writing to the database. It returns nothing to the code that fired it.

core reaches wp_footer→your callback runs→(nothing returned)

Filter: "change this value"

Receives a value, modifies it and must return it. It should work in isolation, with no side effects such as printing or changing globals.

"Hello"→callback A→callback B→"HELLO ★"
add_action( 'wp_footer', 'my_footer_note', 10, 1 ); add_filter( 'the_title', 'my_title_tweak', 10, 1 ); // signature: add_filter( string $hook_name, callable $callback, int $priority = 10, int $accepted_args = 1 )

Two details trip people up: priority (default 10; lower numbers run earlier, and equal priorities run in the order they were added) and the fact that removing a callback requires the exact same callback and priority you added it with, otherwise nothing is removed and you get no warning. Try both next.

4 Where content lives: the database

WordPress keeps its data in a small set of tables in a MySQL-compatible database (the standard core set is about a dozen tables, with a prefix that defaults to wp_ and is set in wp-config.php). Pick a kind of content and see which tables hold it.

The surprise for newcomers is that wp_posts holds far more than blog posts: pages, navigation menu items and more are rows in it, distinguished by a type column. Custom post types (a later lesson) use the same table.

6 Where does my code go?

One of the questions below uses a "Case Study" content type, so first, what is that? In WordPress a content type (technically a custom post type) is a kind of content with its own admin menu, fields and URLs, alongside the built-in "Posts" and "Pages". An agency site might want "Case Studies" (client, challenge, results) or a restaurant might want "Menu Items". Underneath, entries are still rows in wp_posts; a column called post_type says which kind each row is. The thing that makes WordPress recognise the kind is a line of code, register_post_type(), and where that line lives decides what happens when the theme changes. Try it:

7 Working locally: wp-env and WP-CLI

You rarely develop against a live site. Two tools cover most of what a developer needs to know first. wp-env (from the Gutenberg project) spins up a local WordPress for building and testing plugins and themes. It runs on Docker by default (plus Node.js and git), serves the site at localhost:8888, and includes a MariaDB database, WP-CLI, Composer and PHPUnit. WP-CLI is the command-line interface for almost anything you can do in the admin, which makes WordPress scriptable for deploys and automation. Tap a command.

Other local setups exist, such as Local and DDEV; they are common choices but not covered by the sources used here.

Debugging starts in wp-config.php. That file sits in the install root, holds the database connection details and other core settings, and is created during setup rather than shipped in the download. WP_DEBUG lives there too and controls whether WordPress reports errors and warnings. Turn it on locally, never leave it on for a live site.

✦ Takeaways & sources

  • WordPress runs on every request: boot, load plugins and theme, parse the request, run the main query, pick a template, print, shut down.
  • Hooks are the extension model. Actions do something at a moment; filters pass a value through callbacks that must return it.
  • Priority and removal have rules: default 10, lower runs earlier, ties run in the order added; removal needs the exact callback and priority.
  • The data is a small set of tables, and wp_posts holds many kinds of content, not just posts.
  • Core is read-only in practice: your work lives in wp-content (themes and plugins); settings live in wp-config.php.
  • Develop locally with something like wp-env, and learn WP-CLI early.
