1 What a theme is made of

A theme is a folder in wp-content/themes/ that controls how the site looks and which template renders each kind of page. There are two main shapes. Classic themes are PHP: template files, a functions.php, and the loop. Block themes describe templates as HTML made of blocks, configured through theme.json. You will meet both, and this course is code-first, so it concentrates on classic themes and treats block themes as something to recognise. Switch the view and click through.

You will also hear "hybrid theme" for a classic theme that adopts some block-theme features. The documentation used for this lesson doesn't define it, so check the current handbook before leaning on the term.

2 The template hierarchy explorer

When a request arrives, WordPress reads the query to work out what kind of page it is (a single post, a category archive, a search), then looks in your theme for template files with matching names, from most specific to most general, and uses the first one it finds. If nothing matches, it falls back to index.php, the only template every theme must have. Pick a kind of request and tick the files your theme has. The winner is highlighted.

The hierarchy is a chain of fallbacks. Specific files (category-news.php) beat group files (category.php), which beat general ones (archive.php), which beat index.php. A good theme stays small by relying on the general files and adds specific ones only where a page genuinely differs.
Who decides the order? WordPress itself, not your files. The priority lists are built into WordPress core: for each kind of request, core builds the list of file names, then looks for each one in turn, in the child theme first and then the parent theme, and uses the first it finds. Nothing inside a template file says "I rank above that one." Your only part is the file name: naming a file the way core expects is how you opt in. (A page's custom template, chosen in the editor through a "Template Name" comment at the top of the file, is the one exception, because the page itself points to it. Developers can also change the lists with filters, but that is an advanced topic.)

3 Template parts and get_template_part()

Repeated chunks (a card, a header, a loop item) live in separate files and are pulled in with get_template_part( $slug, $name, $args ). It looks for {slug}-{name}.php first, then {slug}.php, and loads the first it finds. If neither exists it quietly does nothing and returns false, so a typo fails silently. Since WordPress 5.5 the $args array is available inside the part. It is for classic themes; block themes use their own template-part mechanism. 4 functions.php and enqueuing assets

functions.php behaves like a plugin that belongs to your theme. Only the active theme's file runs, and it loads after the plugin files. Typical contents: a setup function hooked to after_setup_theme that calls add_theme_support(), registers navigation menus and loads translations, plus your own hooks and helper functions. The handbook's guidance on the plugin question matches the code-placement idea from the last lesson: features that should exist whatever the site looks like belong in a plugin, because theme features vanish when the theme is switched.

5 Child themes: who wins?

A child theme extends a parent so you can change it without editing its files, and your changes survive parent updates. The minimum is a style.css whose header has a Template field matching the parent's folder name exactly; functions.php is optional. Two rules matter. For templates, a child file with the same name overrides the parent's, but a more specific template in the parent still beats a more general one in the child, because the hierarchy order comes first. For functions.php, the child's file loads just before the parent's and does not replace it, so never copy parent functions into the child: duplicate function names cause fatal errors. For parent styles there is no single fixed method: if the parent loads its own stylesheet and the child's, the child needs no extra code; otherwise you enqueue the parent's (or the child's) style.css yourself, so check what the parent actually loads.

✦ Takeaways & sources

  • A theme is a folder with conventions. Classic themes require index.php and style.css; block themes require index.html (in templates/) and style.css, with theme.json as the foundation of block theming.
  • The template hierarchy picks the file: most specific to most general, falling back to index.php. Learn the chains for the page types you use most.
  • Use template parts for repeated chunks; remember get_template_part() fails silently if nothing matches.
  • Put theme setup and enqueues in functions.php, hook assets to wp_enqueue_scripts, and don't hard-code asset tags.
  • Child themes override by filename, but hierarchy specificity still wins; their functions.php adds to the parent's rather than replacing it.
