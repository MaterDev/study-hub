1 Caching layers: where a request is answered

A WordPress page is built on demand: PHP runs, the database is queried, the theme's template prints HTML. That is expensive to repeat for every visitor, so sites add caches that answer earlier in the chain. The WordPress optimization guide describes several: page caching saves pages as static files so PHP barely runs, browser caching lets a returning visitor reuse files they already hold, a persistent object cache reduces trips to the database, and a CDN serves static files from servers closer to the visitor.

My own simplifications in the model: the CDN serves static files only (some CDNs can also cache whole pages), and a logged-in editor bypasses the page cache. Caching plugins commonly skip cached pages for logged-in people, but that is a setting and varies, so treat it as typical rather than guaranteed.

2 Core Web Vitals: what moves which metric

web.dev defines three Core Web Vitals. Largest Contentful Paint (LCP) measures loading and is good at 2.5 seconds or less. Interaction to Next Paint (INP) measures responsiveness and is good at 200 milliseconds or less. Cumulative Layout Shift (CLS) measures visual stability and is good at 0.1 or less. A page passes when it meets those targets for at least 75 percent of visits, measured separately for mobile and desktop.

Most WordPress performance work is images, fonts, scripts and caching. The skill is knowing which fix helps which number. Themes queue scripts and styles with the enqueue functions, and that is where the loading strategy lives: loading a script only where it is needed, and deferring it where possible, keeps the main thread free. Match each problem to the metric it mainly hurts.

The three metric names and thresholds are from web.dev. Which problem maps to which metric is my own simplified teaching mapping; real pages often affect more than one metric, and the answers note where.

3 Accessibility in theme output

Accessibility is mostly decided by the markup your theme prints, which makes it a front-end developer's job in WordPress. The W3C's WCAG 2.2 is the standard. Four failures show up in themes again and again: form fields without a real label, text without enough contrast, no visible keyboard focus, and no landmarks or skip link to jump past the menu. The contrast criterion (1.4.3, Level AA) asks for at least 4.5:1 for normal text and 3:1 for large text.

    4 How a site gets compromised

    Most compromises are not clever. The common routes are ordinary: software with a known, already-fixed flaw that was never updated, a plugin that is no longer maintained, and credentials that are weak, reused or shared. The WordPress hardening guide's advice follows from that: keep WordPress and plugins updated, delete plugins you do not use, install from trusted sources, use strong generated passwords with two-step authentication, and keep tested backups of the files and database.

    5 Three code habits: validate, escape, authorise

    You met escaping in lesson 2.1: escape late, at the moment of output. The WordPress security handbook states the principle as never trusting user input, prefers validating and rejecting bad data over cleaning it, and says to escape as late as possible. Two more habits sit beside it. A nonce is a token that helps protect a form or link from being triggered by someone else's page (a forged request). It is not a login check: the handbook says nonces should not be relied on for authorisation, and to protect actions with a capability check such as current_user_can(). Pick the habit that fits each situation.

    ✦ Takeaways & sources

    • Performance work is mostly images, scripts and caching. Cache so PHP and the database run less; fix the metric that is actually failing.
    • Core Web Vitals: LCP 2.5 s or less, INP 200 ms or less, CLS 0.1 or less, at the 75th percentile (web.dev).
    • Accessibility is theme markup: real labels, 4.5:1 text contrast, visible focus, landmarks and a skip link.
    • Most compromises are ordinary: unpatched or abandoned plugins and weak credentials. Updates, fewer plugins, strong credentials with two-step authentication, least-privilege roles and tested backups cover most of it.
    • In code: validate input, escape late, and protect actions with a nonce plus a capability check. A nonce alone is not authorisation.
