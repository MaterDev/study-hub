1 What "headless" means

In a classic site, WordPress does two jobs: it stores and edits content, and it renders the HTML that visitors see through a theme. Headless removes the second job. WordPress stays the place editors write and manage content; a separate application (a JavaScript framework, a static site, a mobile app) fetches that content over an API and renders the pages itself.

The WordPress REST API is the built-in way to do this. The handbook describes it as a feature that lets external applications and your own code read and write site data, using JSON, and that also powers the block editor. Endpoints are URLs that represent WordPress data types such as posts, pages and taxonomies. WPGraphQL is a plugin that offers a GraphQL schema as an alternative. Lesson 2.2's custom post types and fields are exactly the data this chapter pulls out.

The attraction is front-end freedom: any framework, any hosting, and a team that never touches PHP. The cost is everything the theme used to do for you. The rest of the lesson makes that cost visible, so you can decide with open eyes.

2 The REST API: ask for posts

The list-posts endpoint is GET /wp/v2/posts under the site's wp-json path. The reference documents parameters such as page (default 1), per_page (default 10), search, status (default publish) and context. Two global parameters shape the response: _fields limits it to the properties you name, and _embed adds linked resources, such as the author, under an _embedded key so you can avoid extra requests. One detail bites everyone once. WordPress returns titles and content as rendered HTML, so a title can contain entities such as &#038;. Insert it as text and you see the entity; insert it as HTML and it displays properly, but now you are putting markup from a database into your page, so only do that for content you trust or after sanitising it (the escaping habit from lesson 2.1 does not go away just because WordPress is no longer printing the page).

What the handbook confirms: the endpoint, the parameters above, and that the schema lists id, date, slug, status, link, title, content, excerpt and featured_media. That title, content and excerpt carry a rendered string, that entities appear in rendered titles, and that responses carry total-count headers for paging, are background knowledge here.

3 Authentication: who is asking?

Public content is readable without logging in; private and password-protected content needs authentication, as does writing. The handbook describes two main routes for your own code. Cookie authentication is built into WordPress: it works for code running inside WordPress as a logged-in user, and requests need a nonce created for the action wp_rest, sent as X-WP-Nonce (the safest way) or _wpnonce. Without the nonce the current user is set to 0, so the request is unauthenticated even if you are logged in. Application passwords, available from WordPress 5.6, are generated on the user's Edit User screen and sent with Basic Auth, only over https. For a separate front-end server, application passwords are the natural fit. 4 REST or WPGraphQL?

WPGraphQL is described on its own site as a free, open-source plugin that provides an extendable GraphQL schema and API for WordPress, with types and fields generated from registered post types and taxonomies. With GraphQL the client writes a query naming exactly the fields it wants, so one request can reach across relationships. REST returns whole resources, but _fields and _embed narrow that gap. 5 Drafts, previews and fresh content

Two things that a theme gave you for free now have to be built. The first is fresh content. A front end like Next.js builds pages ahead of time and caches them. Its Incremental Static Regeneration documentation describes two ways to refresh: time-based (a revalidate interval, after which the next request still receives the stale page while a new one is generated in the background) and on-demand (calling revalidatePath or revalidateTag to invalidate cached entries). Something has to tell the front end that WordPress changed; a webhook sent when a post is updated is the usual answer (background knowledge, you build it). The second is preview. Walk through what happens when an editor updates a post, and what changes if they click Preview on a draft.

The revalidation behaviour is from the Next.js ISR guide (Next.js is one example of a front end; others have equivalents). The webhook and the preview route are my own description of the usual design: to preview an unpublished post, the front end must fetch the draft with credentials (the REST posts reference lists draft among the allowed status values but does not say what authentication it needs) and must skip its cache for that request. WPGraphQL lists a Previews guide, which I did not read.

7 Is headless worth it?

Headless is a good answer to some problems and an expensive answer to most. Tick what describes your project. The scoring is my own rough heuristic, meant to make the trade visible rather than to decide for you.

VERDICT
The two-systems cost. A headless project is two deployments joined by an API: WordPress needs a PHP and database host, regular updates and backups, and a locked-down admin; the front end needs its own hosting and build pipeline; between them sit credentials, cross-origin settings and a webhook. Each has its own monitoring and its own way to fail at 2 a.m. If the team cannot own both, the savings in front-end flexibility are spent on operations. (My own summary of the costs.)

✦ Takeaways & sources

  • Headless means WordPress stores and edits content while a separate application fetches it and renders the pages.
  • REST: GET /wp/v2/posts with parameters like per_page, status, _fields and _embed; custom types need show_in_rest.
  • Authentication: public content needs none; cookie plus nonce is for code inside WordPress; application passwords (WordPress 5.6 onwards) over https suit a separate server.
  • WPGraphQL offers a schema-based alternative where the client names the fields it wants; REST can narrow responses with _fields and _embed.
  • Freshness and previews are yours to build: time-based or on-demand revalidation, and an authenticated draft fetch for preview.
  • Headless trades plugin compatibility and editor previews for front-end freedom. If the team cannot own two deployments, do not.
