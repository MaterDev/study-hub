The practical skill this lesson builds: given a request, know where it belongs before you start building. Pick a home for each request. Notice how often the right answer is something the platform already ships.

4 Themes: one surface among several

A theme controls the online-store experience. It is built with Liquid (Shopify's templating language) plus HTML, CSS, JavaScript and JSON, and you can start from Shopify's Skeleton theme or customise an existing one. The current architecture is called Online Store 2.0: it lets you add and remove sections on any template and prepares a theme for app blocks. Tooling in the docs: the Shopify CLI to run and preview a theme locally, Theme Check to catch errors, and a GitHub integration for managing theme code from the admin. The next lesson takes the theme apart; here, what matters is the boundary.

A theme owns

  • How the storefront pages look and behave
  • Templates, sections and the theme editor experience
  • Front-end JavaScript on those pages (for example cart interactions via the Ajax and Section Rendering APIs)
  • Theme settings and translations

A theme does not own

  • Checkout, customer accounts and POS (separate surfaces)
  • The data itself: products, customers and orders live in Shopify
  • Business logic that has to run inside Shopify, such as discount and delivery rules
  • Back-end work for the merchant: sync, reports, workflows

5 Apps: what they are and where they appear

In the docs' framing, an app is a set of declared components. Shopify runs most of them; the developer hosts only the backend. Click a component.

Apps can appear in the app's own admin page (App Home), the admin, checkout, customer accounts, the online store (alongside the theme) and point of sale. They are distributed one of two ways:

Public app

  • Listed in the Shopify App Store
  • Shopify reviews each listing before it goes live
  • Once approved, any merchant can install it
  • Billing plans are defined in the listing

Custom app

  • Installed directly by a single organisation
  • No App Store listing and no review
  • The usual route for work built for one client

6 The APIs: who is calling?

"The Shopify API" is really several, each aimed at a different caller. Each has its own token and header, and access scopes control what a token can read and write. Pick who is calling.

Shopify releases a new API version every quarter and supports each for a year, so integrations need a plan for version upgrades; the changelog lists deprecations.

7 Stores and plans: what you work in

As a developer you rarely work in the merchant's live store first. Click each kind of store.

Plans matter to you in practice because some capabilities depend on the tier. The docs name Basic, Grow, Advanced and Plus for development stores (and list more tiers on the plans page, such as Starter, Lite, Retail and enterprise). The detail of what each plan unlocks is the kind of thing to check at the time of scoping, not to assume from memory.

8 What changes fast

This lesson is a map, and the platform keeps redrawing parts of it. Before you scope work, verify these against current documentation:

My own judgment, not from the docs: when a request arrives, the cheapest question to ask is "does the platform already do this?" Admin configuration and built-in features cost nothing to build and nothing to maintain. A theme change is next, then an app. Headless is the most expensive answer, and it only pays when you need a front end Shopify's theme system can't give you.

✦ Takeaways & sources

  • Shopify is several surfaces, not one: admin, online store (a theme), checkout, customer accounts, POS, with apps and APIs around them.
  • Know who owns what: the merchant runs the admin; developers build themes and apps; Shopify runs checkout and the core data.
  • A theme owns the storefront pages, not checkout, the data, or logic that must run inside Shopify.
  • An app is a set of declared components (auth, extensions, Functions, data storage, webhooks); you host the backend, Shopify runs the rest. Public apps are reviewed and listed; custom apps serve one organisation.
  • There are several APIs for different callers, each with its own token and scopes, versioned quarterly.
  • Develop in a dev store, and use a client transfer store when the merchant will own the result.
  • Ask "does the platform already do this?" first.
