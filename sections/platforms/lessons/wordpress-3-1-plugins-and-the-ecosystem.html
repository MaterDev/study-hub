1 A plugin is a package of PHP

The plugin handbook describes plugins as packages of code that extend the core functionality of WordPress. They are made of PHP and can include other assets such as images, CSS and JavaScript. You already know the mechanism from the hooks lesson: a plugin is mostly a place to put add_action() and add_filter() calls that do not belong to a particular theme.

The smallest possible plugin is one PHP file in wp-content/plugins with a header comment. The header reference says the only required field is Plugin Name; the others (version, author, licence, minimum WordPress and PHP versions and so on) are optional but are what you read when judging a plugin. 2 Plugin, theme or must-use?

The usual rule of thumb: if the feature should still exist after the theme is changed, it belongs in a plugin. Custom post types and fields for the client's data are the classic case (the content-types lesson raised this). A theme should own presentation. Registering content types in functions.php means the content vanishes from the admin the day the theme changes.

A third home exists. Must-use plugins live in wp-content/mu-plugins. They load automatically, before normal plugins, in alphabetical order, and cannot be switched off from the admin: you delete the file. The handbook lists the trade-offs: no activation hooks run, there are no update notices, and only PHP files directly in that folder load (a subfolder needs a small loader file). Choose the home for each feature.

The scenarios and their "best home" answers are my own teaching judgement applying the handbook's description; real projects argue about edge cases.

4 Vetting a plugin before you install it

Every plugin is a dependency you now maintain. Before installing, read its signals. The WordPress.org plugin directory shows many of them on the plugin's page, and its guidelines (GPL-compatible code, no trialware, no tracking without consent, no loading executable code from unapproved sources) set a baseline for plugins listed there. Premium plugins sold elsewhere are not covered by those guidelines, so more of the checking is yours. Below, set the signals for a made-up plugin and read the verdict. 5 When the site breaks: plugin bisection

A white screen, a broken layout or a JavaScript error appeared after an update. The standard way to find a plugin culprit is elimination: on a staging copy, deactivate plugins, test, reactivate some, test again. Doing it one plugin at a time takes up to ten tests for ten plugins. Splitting the active set in half each time takes four. Here the site has ten plugins and exactly one is the cause (it changes each round). Switch plugins off, press Test the site, and name the culprit when you are sure.

    SITE STATUS
    Not tested yet
    Tests run: 0

    Real life is messier than this model: sometimes two plugins conflict only together (so the problem persists until both are off), sometimes the theme is the cause (switch to a default theme as well), and you do this on a staging copy so visitors never see it. A broken plugin can also lock you out of the admin; renaming its folder over SFTP deactivates it. That last point and the staging advice are standard practice from background knowledge rather than from the pages cited below.

    6 Licences, renewals and the audit sheet

    Plugins in the directory must be GPL-compatible, so the code itself is free to use. Paid plugins usually sell something else: updates, support and sometimes a licence key that stops updates when it expires. Ask before you buy: whose account holds the licence, who gets the renewal email, and what happens to the site when it lapses (it keeps running, but you stop receiving updates, which is a security matter). Put client-critical licences in the client's name where you can, and record them in the handover. That advice is my own practice-based synthesis.

    ✦ Takeaways & sources

    • Every plugin is a dependency you now maintain. Fewer, better plugins beat many.
    • A plugin is PHP in a folder with a header; only Plugin Name is required, but the other fields are what you read when judging it.
    • Features that must survive a theme change go in a plugin; must-use plugins are always on, load first, and get no update notices.
    • Vet before you install: update activity, support, compatibility, code and licence terms, not install counts.
    • Find a conflict by elimination, halving the active set, on a staging copy.
    • Know who owns the licence and who receives the renewal.
