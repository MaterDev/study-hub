1 What "orchestration" actually means

"Multi-agent" is not one thing. Before the patterns, hold onto one distinction that runs through everything: who decides the flow?

🧠 Orchestrated by the LLM

You hand a model tools and other agents, and let it decide who runs, in what order, and when to stop. Flexible, handles open-ended work — but less predictable.

⚙️ Orchestrated by code

You define the flow in software: route on outputs, chain step to step, loop an evaluator, fan out in parallel. More deterministic in cost, speed, and behavior.

The one rule everyone agrees on: start with the simplest thing that could work — usually a single agent with good tools — and only add multi-agent complexity when it demonstrably improves the outcome. Anthropic, Cognition, OpenAI and LangChain all say versions of this. Multi-agent is a cost you pay for a specific benefit, not a default.

3 Anthropic's design principles

Anthropic's "How we built our multi-agent research system" (June 2025) is the most detailed production account we have. It uses an orchestrator-worker setup: a lead (Opus) plans and spawns worker subagents (Sonnet) that search in their own context windows and return condensed findings. It beat single-agent Opus by 90.2% on their internal research eval.

The central tradeoff: tokens

Multi-agent systems are, bluntly, a way to spend more tokens productively — in parallel, across separate context windows. That only pays off when the task is valuable enough to justify the burn.

In Anthropic's BrowseComp analysis, token usage alone explained ~80% of the performance variance; adding tool-call count and model choice explained ~95%. Upgrading the model was a bigger lever than doubling the token budget.

Scale effort to complexity

Early versions spawned 50 subagents for simple queries. The fix was baking explicit effort rules into the orchestrator's prompt:

S
Simple fact-finding — 1 agent, 3–10 tool calls
M
Direct comparison — 2–4 subagents, 10–15 calls each
L
Complex research — 10+ subagents with clearly divided responsibilities

The delegation lessons

Vague instructions ("research the semiconductor shortage") caused two subagents to redundantly research 2025 supply chains while a third wandered into the 2021 crisis. The lessons that fixed it:

  • Give each subagent a full spec: objective, output format, tool/source guidance, and explicit task boundaries.
  • Start wide, then narrow — broad queries first, then progressively focus, like an expert researcher.
  • Parallelize deliberately — lead spins up 3–5 subagents at once, each calling 3+ tools in parallel. Cut research time up to 90% on complex queries.
  • Write big outputs to a filesystem and pass lightweight references back — avoid the "game of telephone" of piping everything through the coordinator's context.
  • Save the plan to memory so it survives context-window truncation past 200K tokens.
  • Verify separately: a dedicated CitationAgent attributes every claim to a source; an LLM-as-judge rubric (accuracy, citations, completeness, source quality) gates the output.

4 The counter-case: when NOT to

One day before Anthropic's post, Cognition published "Don't Build Multi-Agents." It's not a strawman — it's a sharp, opposed argument, and taking it seriously will make you better at this.

Its thesis: reliability comes from context engineering, and parallel subagents fragment context. Two principles it says you should rarely violate: share full agent traces, not just messages; and actions carry implicit decisions, and conflicting decisions produce bad results.

The Flappy Bird failure

✂️
Task "build Flappy Bird" is split: subagent A does the background + pipes, subagent B does the bird.
🎨 🐦
A builds a Super Mario-style background; B builds a bird that moves wrong. Neither can see the other's work, so their implicit style decisions conflict.
🧩💥
The final agent is stuck reconciling two mismatched halves. Even copying the full task to both doesn't help — they still can't see each other.

Cognition's prescription: default to a single-threaded linear agent (continuous context, no cross-agent conflicts). When it overflows the context window, don't fan out — compress the history with a dedicated summarizer model.

The reconciliation. These two posts agree more than they look. Both say context engineering is everything. Both agree tightly-coupled work like most coding is a poor fit for parallel subagents. The real disagreement is narrow: for breadth-first research with genuinely independent sub-questions, fan-out works (Anthropic). For tightly-coupled long tasks, it fails (Cognition). The deciding variable is how independent your subtasks truly are, and how much shared context they need.

6 Recipes you can steal

Breadth-first research

Orchestrator-worker. Best when sub-questions are independent and the task is high-value.

Lead plans → saves plan to memory → spawns 3–5 subagents (each: scoped objective + output format) → subagents search in parallel, return condensed findings → lead synthesizes, spawns more if gaps → CitationAgent attributes claims → LLM-judge rubric gate → deliver
Deep single-topic research

Single-threaded + compression. Best when the topic is deep and interdependent, not broad.

One agent searches iteratively → when context fills, a summarizer compresses history into key decisions/findings → agent continues with the compressed context
Report generation

Sequential pipeline + evaluator-optimizer. Best when quality criteria are explicit.

Research → outline (gate: covers the brief?) → draft → evaluator critiques on a rubric → revise → loop until pass or retry-cap
Mixed prompt workloads

Router with model tiering. Best for a stream of differently-shaped requests.

Classify incoming prompt → route (quick-lookup→Haiku · analysis→Sonnet · hard→Opus) → specialist executes → optional critic pass
High-confidence judgment

Voting. Best for contested calls: moderation, vuln flagging, disputed facts.

Run the same eval prompt N times (or N variant prompts) in parallel → aggregate by threshold / majority vote

Failure modes to name out loud

🔁
Compounding errors — agents are stateful; one bad step derails the run. Add checkpoints, retries, and let the model adapt to tool failures.
🧩
Context fragmentation — parallel agents making conflicting implicit decisions (the Flappy Bird problem).
📈
Over-spawning — 50 agents for a trivial query. Fix with explicit effort-scaling rules.
🎲
Non-determinism — tiny orchestrator-prompt tweaks ripple unpredictably. Needs tracing and end-state (not step-by-step) evaluation.
