2 Why models are good at CLIs

This isn't a coincidence or a hack — it falls out of how the models were trained and how shells work:

📚
They've read the whole internet's worth of shell. git commit, grep -r, curl -X POST, npm run build appear millions of times in the training data — man pages, Stack Overflow, READMEs, CI configs. The model has strong priors for the exact flags and idioms. An MCP tool schema you wrote last week has zero training signal; the model learns it fresh, in-context, every session.
🔗
Pipes compose without you designing an API. Unix tools chain with |: the output of one becomes the input of the next. The agent can read a log, keep only errors, sort, dedupe, and count — in a single line — without you having built a "filter-and-count" tool. Composition is free.
🔁
The loop is tight and text-native. Run command → read stdout/stderr → adjust → run again. Plain text in, plain text out, exit codes for success/failure. No schema round-trips, no serialization layer, no client that has to be running.

Watch a pipeline the agent can write in one shot — no custom tool required:

rg "ERROR" logs/ | cut -d: -f1 | sort | uniq -c | sort -rn | head
"find ERROR lines across logs/"

3 The token tax of MCP

The diagram's "burns context tokens" arrow is the crux, and it's measured, not vibes. Per Anthropic: most MCP clients load every connected tool's definition into the context window up front, before the agent has even read your request. Connect enough servers and that's a six-figure token bill on every turn. Drag the slider:

MCP schemas (upfront)
—
CLI (per command)
~400 tok

Anthropic's worked example: an agent connected to many servers spent 150,000 tokens on tool definitions + intermediate results; rewriting it so the agent writes code to call tools on demand dropped it to 2,000 tokens — a 98.7% cut. A CLI command the model already knows costs ~nothing upfront: just the command it types plus the output you let through. (Second tax the post flags: with direct tool-calls, big intermediate results — a transcript, a 10k-row sheet — flow through the model twice. The CLI/code path filters before anything hits context.)

4 "MCP mostly wraps the CLI"

The diagram's sharpest jab: an MCP: Git server or MCP: Docker server is often a thin layer that... shells out to git and docker. For a coding agent already sitting in a sandbox with those binaries, you've added a schema-loading, process-running, token-costing layer in front of a tool the model already invokes fluently.

🎁As one write-up put it: wrapping a tool the agent already knows how to invoke "adds cost without adding safety." The agent didn't gain a capability — it gained a middleman. The wrapper only pays off when it adds something the raw CLI can't: scoped permissions, discovery, a non-CLI backend, an audit trail (see §5).

5 Where MCP actually wins

The honest other half — and the diagram agrees (its "enterprise, non-dev, regulated" box). MCP is an open standard (Anthropic, 2024; now adopted by Microsoft, OpenAI, Google) that exists to solve real problems the CLI doesn't:

Reach for the CLI when…

  • It's a trusted, terminal-native coding agent (Claude Code, a sandboxed dev loop)
  • The tool is a binary the model already knows (git, rg, docker, gh, build scripts)
  • You want fast iteration and cheap context
  • You need ad-hoc composition (pipe/filter/transform)

Reach for MCP when…

  • Hosted / multi-tenant / consumer apps — permissions must be scoped per user or org (close to non-negotiable)
  • The backend isn't a CLI — a SaaS API, a governed database, an internal service
  • You need discovery — the agent (or another team's agent) can ask "what can you do?" and get a typed answer
  • Regulated / audited environments needing structured logging, allow-lists, and a standard interface
  • Non-developer or cross-client use — one server, many agents/hosts

The CLI's own limits are the mirror image: no standard schema, no built-in discovery (the agent can't query what a command can do), and — critically — letting an LLM generate shell commands means a prompt injection can become arbitrary code execution unless you sandbox hard (§7).

6 The resolution: write code to call tools

Here's the twist that makes this more than a flame war. Anthropic's own fix for MCP's token tax isn't "abandon MCP" — it's "let the model write code that calls the tools," loading only the definitions it needs, on demand. Cloudflare shipped the same idea as "Code Mode." That's the CLI philosophy — the model is great at writing code/commands; lean on that — applied to MCP.

Direct tool-calls (token-heavy)

// every tool schema preloaded into context
// each result flows back through the model
TOOL gdrive.getDocument(id) → 50k-token transcript
TOOL salesforce.updateRecord(… same transcript …)
// transcript passes through context twice

Agent writes code (token-light)

import * as gdrive from './servers/google-drive';
import * as sf from './servers/salesforce';
const t = (await gdrive.getDocument({id})).content;
await sf.updateRecord({id, data:{Notes:t}});
// transcript never enters the model's context

So the real axis isn't "CLI vs MCP" — it's "tool-call each thing (schemas + results through the model)" vs "let the model drive a shell/runtime." The CLI is the zero-setup version of the winning side. MCP-plus-code-execution gets you the standard and the efficiency — at the cost of running a sandbox.

under the hood

Why this is the same insight as "give it a terminal"

A shell is just a code-execution environment the model already has priors for. "Write bash" and "write a TS script that calls MCP tools as functions" are the same move: keep tool definitions and intermediate data out of the context window, and let a runtime — not the model's attention — do the plumbing. Both beat spraying 200 tool schemas into every prompt.

7 Decision guide + doing CLI-first safely

Answer three questions for your setup:

1. Who runs the agent?
2. What's the tool behind it?
3. Environment?

If you go CLI-first (the right default for a trusted coding agent), do it safely:

🧱
Sandbox the shell. An LLM emitting shell commands + untrusted input (a web page, an issue, a file) is a prompt-injection path to arbitrary code execution. Run in a container/VM with no secrets, least privilege, and network egress limits.
✅
Allow-list, don't free-for-all. Permit git, rg, npm test, your build scripts; gate destructive/irreversible commands behind confirmation. This is the safety MCP would otherwise provide — you're just providing it at the shell layer.
🪵
Keep an audit trail. Log the commands the agent runs. In regulated contexts this is exactly the structured accountability that pushes teams to MCP — if you can't produce it at the CLI layer, that's a signal to use MCP.
🧩
Hybrid is fine — and often best. CLI for the git/build/test loop; MCP (ideally via code execution) for the governed SaaS/database/multi-tenant pieces. It's not religion; match the mechanism to the tool.

✦ Takeaways & sources

  • For trusted coding agents, CLI-first is the sane default: models already know shell tools, pipes compose for free, and you pay ~no upfront token tax.
  • MCP's cost is real and measured — schemas load into context up front (Anthropic's example: 150k→2k tokens once the agent writes code instead).
  • Many dev MCP servers just wrap a CLI the agent already knows — a middleman that "adds cost without adding safety" unless it adds scoping/discovery/a non-CLI backend.
  • MCP genuinely wins for hosted/multi-tenant/regulated/non-dev and non-CLI systems (standard interface, per-user auth, discovery, audit).
  • The real fix is "let the model write code to call tools" — the CLI is the zero-setup version of that; MCP+code-execution is the governed version.
  • CLI-first ≠ careless: sandbox, allow-list, and log — that's how you get the CLI's speed without giving up MCP's safety.
