1 What context engineering is

Prompt engineering is writing good instructions. Context engineering is curating everything the model sees on each call: instructions, tool definitions, files and results it has pulled in, and the running message history. Anthropic calls it iterative, because the curation happens again every time something is passed to the model.

The reason to care is a property of the models. Anthropic's engineering team calls it context rot: recall accuracy declines as the window fills, so context is a finite resource with diminishing returns, an "attention budget" that each new token draws down. The aim: the smallest set of high-signal tokens that gets the outcome you want.

2 The window is a budget

Claude Code's best-practices guide opens by saying most of its advice follows from one constraint: the context window fills up fast, and performance degrades as it fills. Each square below is about 2k tokens of a 200k window. Drag the sliders and watch the desk fill. The numbers are illustrative; run /context in a real session for yours.

Assumptions: ~25k fixed overhead; ~14 tokens per CLAUDE.md line; ~450 per tool schema; ~3k per file read; a sub-agent returns ~1.5k per ten files it reads, in its own window (Anthropic's post cites 1,000–2,000-token summaries). Some models offer a 1M window; the logic is the same, just later.

The practical rule: anything that must survive a long session belongs in a file that gets re-injected (project-root CLAUDE.md, a rule without paths:, auto memory, a plan file), never only in something you typed. You can also steer the summary: /compact Focus on the API changes, or add a CLAUDE.md line such as "When compacting, always preserve the full list of modified files and any test commands."

4 A CLAUDE.md that earns its lines PART 1

CLAUDE.md is read at the start of every conversation, so every line is a permanent tax on the budget. The docs' guidance is under 200 lines per file, and their test for each line is: "Would removing this cause Claude to make mistakes?" If not, cut it. A bloated file does worse than a short one: rules get lost and Claude starts ignoring half of it. You are the editor. Decide each candidate line and watch your file take shape.

Scope by how often a rule applies. Always-true rules → project-root CLAUDE.md. One-area rules → .claude/rules/ with paths: frontmatter. Sometimes-needed knowledge → a skill, loaded on demand. Personal, per-project → CLAUDE.local.md (gitignored); personal everywhere → ~/.claude/CLAUDE.md. And remember: CLAUDE.md is advice; hooks are enforcement. Claude treats memory files as context, not enforced configuration, so anything that must happen every time belongs in a hook.

/init drafts a starter file · /memory opens what loaded · /doctor proposes cuts for content Claude can derive from the codebase · block-level HTML comments are stripped before injection, so maintainer notes are free.

6 Conductor: memory that lives in the repo PART 2

Part 1 manages one session's window. Conductor asks what happens across sessions. Its premise, from Google's launch post (17 Dec 2025): agents often start building before anyone has pinned down what is being built, and project context lives in chat logs, which are temporary. The fix is context-driven development: context, specs and plans live as Markdown in the repository, so they persist across sessions, machines and teammates. It launched as a preview extension for Gemini CLI; the project's repository now describes it as a plugin for several agents, including Claude Code ("Measure twice, code once", Apache 2.0).

Read the caveats. Google labels it a preview, and brownfield (existing codebase) support was described as an early first step. The README warns spec-driven work can raise token consumption, especially on larger projects. revert rolls back git commits, so it changes repository history. The launch post is promotional and publishes no quality or performance data, so the case for it rests on the reasoning here, not on measurements.

8 Putting the two parts together

Conductor looks new, but it is the Part 1 habits made durable. Read each row left to right. The mapping is my synthesis, not a claim from any source.

The honest trade-off. Everything Conductor writes down is context you must keep true. A stale tech-stack.md misleads an agent just as an over-long CLAUDE.md does, and extra planning costs tokens and time. The Part 1 test applies to those files too: would removing this line cause a mistake? Use the full method where work spans sessions, people or days; use the lighter habits where it doesn't. ✦ Takeaways & sources

  • Context engineering = curating everything in the window, not just writing a prompt. Context rots as it fills, so aim for the smallest high-signal set.
  • Claude Code best practices are context management: give it a way to verify, explore then plan then implement, be specific, delegate reading to sub-agents, /clear early.
  • CLAUDE.md is a budget line item: under ~200 lines, only what removal would break, scoped by how often it applies, with hooks for anything that must be enforced.
  • Put what must survive in files that get re-injected, not in chat; compaction summarizes the conversation away.
  • Conductor makes the habit durable: context, spec and plan live in the repo as Markdown; you review the plan before code; every session starts from the same files.
  • Pay for the heavier method only when the work needs it. Both approaches fail the same way: stale or bloated context.
