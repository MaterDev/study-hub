1 The problem WebSockets solve

HTTP was designed around a simple idea: the client asks a question, the server answers, and the conversation ends. That's perfect for loading a webpage. It's terrible for anything that needs to feel "live" — chat apps, live sports scores, multiplayer games, collaborative docs, stock tickers.

📮Analogy: Regular HTTP is like mailing a letter every time you want to ask your friend something — you write it, send it, wait for a reply letter, and the relationship ends until you write again. A WebSocket is like getting your friend on a phone call: you open the line once, and after that either of you can just talk, any time, with no envelope required.

Before WebSockets existed, developers faked "live" behavior with tricks like polling (asking "anything new?" every few seconds) or long-polling (asking once and having the server hold the request open until it has something to say). Both work, but both waste connections, add latency, and don't let the server push data the instant it happens.

WebSockets (standardized as RFC 6455) fix this by upgrading a single HTTP connection into a persistent, full-duplex pipe. "Full-duplex" just means both sides can send whenever they want, independently, over the same open connection — no more request/response ping-pong.

3 The handshake, step by step

A WebSocket connection is born as a completely normal HTTP request. The trick is a special Upgrade header that asks the server to switch protocols on this same TCP connection. Press play to walk through it.

1. Client → Server — a normal-looking HTTP request, asking to upgrade
GET /chat HTTP/1.1 Host: example.com Upgrade: websocket Connection: Upgrade Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ== Sec-WebSocket-Version: 13
2. Server → Client — "101 Switching Protocols" instead of the usual 200 OK
HTTP/1.1 101 Switching Protocols Upgrade: websocket Connection: Upgrade Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
3. The TCP connection stays open — it's no longer HTTP, it's now a raw WebSocket pipe
Both sides can now send/receive WebSocket "frames" at any time, in either direction, until either side closes the connection.

Sec-WebSocket-Accept is just a hash of the key the client sent, combined with a fixed magic string, proving the server actually understood the WebSocket protocol (not just some proxy that ignored the Upgrade header). You'll never compute this by hand — the browser and your server library both do it for you.

The good news: you will almost never build a frame by hand. Your browser's WebSocket object and server libraries like ws handle all of this framing for you. It's worth knowing it exists because it explains two real things you'll bump into: why WebSocket traffic is so much lighter than HTTP per message (tiny 2–14 byte overhead vs. hundreds of bytes of headers), and why client-to-server frames are always masked (a security measure against cache-poisoning attacks on shared proxies).

6 Writing it: client + server code

Here's the entire thing end to end — a browser client and a Node.js server using the popular ws package.

// Runs in the browser, no library needed — WebSocket is built in
const socket = new WebSocket("wss://example.com/chat");

socket.addEventListener("open", () => {
  console.log("connected");
  socket.send("hello from the client");
});

socket.addEventListener("message", (event) => {
  console.log("server says:", event.data);
});

socket.addEventListener("close", (event) => {
  console.log("closed", event.code, event.reason);
});

socket.addEventListener("error", (err) => {
  console.error("socket error", err);
});
// npm install ws
const { WebSocketServer } = require("ws");

const wss = new WebSocketServer({ port: 8080 });

wss.on("connection", (socket, req) => {
  console.log("client connected from", req.socket.remoteAddress);

  socket.on("message", (data) => {
    console.log("received:", data.toString());
    // broadcast to everyone else connected
    wss.clients.forEach((client) => {
      if (client !== socket && client.readyState === 1) {
        client.send(data);
      }
    });
  });

  socket.on("close", () => console.log("client disconnected"));
});
// Naive connections die silently (wifi drop, laptop sleep, proxy timeout).
// Always plan to reconnect with backoff.
function connect() {
  const socket = new WebSocket("wss://example.com/chat");
  let retryDelay = 1000;

  socket.addEventListener("open", () => { retryDelay = 1000; });

  socket.addEventListener("close", () => {
    setTimeout(connect, retryDelay);
    retryDelay = Math.min(retryDelay * 2, 30000); // cap at 30s
  });

  return socket;
}

7 Choosing the right tool

WebSockets aren't always the answer. Here's how they stack up against the alternatives:

ApproachDirectionLatencyBest for
Short pollingClient asksPoorRarely-changing data, simplest to build
Long pollingClient asks, server holdsOkayLegacy support, infrequent updates
Server-Sent EventsServer → Client onlyGoodLive feeds, notifications, one-way streams
WebSocketsBoth ways, any timeBestChat, multiplayer, collaborative editing, trading
WebRTCPeer-to-peerBestVideo/audio calls, direct browser-to-browser data

Rule of thumb: if the server only needs to notify the client and the client rarely talks back, SSE is simpler and rides on plain HTTP. Reach for WebSockets when both sides need to talk often, in real time, in either direction.

8 Pitfalls nobody warns you about

🔌
Connections die silently. Wifi hiccups, laptops sleep, corporate proxies kill idle connections. Always write reconnect-with-backoff logic (see the code tab above) — don't assume "connected" means "still connected."
💓
You need heartbeats. TCP alone won't tell you a connection is dead for a long time. Most WebSocket libraries support ping/pong control frames — send a ping every 20–30 seconds and close the connection if no pong comes back.
📈
Scaling is different from HTTP. A WebSocket connection is stuck to one server process for its whole life. Load balancers need "sticky sessions," and broadcasting to all connected clients across multiple server instances usually requires a pub/sub layer (Redis, NATS) to fan messages out.
🔐
Auth isn't automatic. The initial handshake can carry cookies or a token in the URL/query string, but after that there's no per-message "Authorization header" like HTTP. Validate identity once at connect time, and re-check for anything sensitive.
🧱
Firewalls and proxies can still block it. Some corporate networks only allow ports 80/443 and inspect traffic; always use wss:// (WebSocket-over-TLS) in production so it looks and travels like ordinary HTTPS.
