1 What this spike is asking

One deployed app answers one question: is host-authoritative multiplayer feasible and performant enough for this fighting game — measured end-to-end in the real problem space, not in theory? It breaks into four sub-questions, one per experiment:

  • Transport — does WebSocket-over-TCP deliver acceptable latency, or does WebRTC beat it? (Lessons 2–3)
  • Sim-snapshot — can the real Phaser fight state be captured, relayed, and rendered on a second client with no local sim? (Lessons 1, 5)
  • Remote-input — can guest input slot into the real input path without touching the combat code, and what's the felt lag? (Lessons 4, 6)
  • Determinism cost — how expensive would it be to make the sim deterministic so rollback reopens? (Lesson 7)

Plus a Summary that scores it all honestly (Lesson 8). Every idea in this whole series exists somewhere in this app.

The moving parts, each tied to a concept you now know:

Transport port

The swappable pipe

A single Transport interface (send/onMessage/close, kind: ws | webrtc-unreliable | ...). WebSocketTransport and WebRTCTransport both implement it, so every experiment runs unchanged on either. Fire-and-forget: no ordering or reliability assumed.

→ Lessons 2 & 3 · src/lib/contracts.ts §1
server/

The relay + loss proxy

One Node process: a /ws relay (forwards frames verbatim), a /signal relay for WebRTC setup, and a LossProxy in front that injects real link-loss to expose TCP head-of-line blocking. Toggle via /api/loss.

→ Lessons 2 & 3 · server/PROTOCOL.md
RemoteInput

The input seam

RemoteInput implements InputProvider feeds the guest's relayed buttons into the sim through the game's existing input interface — zero changes to CombatSystem. An input-delay buffer sits here as a tunable knob.

→ Lessons 4 & 6 · NetFightScene subclass
snapshotCodec

The snapshot capture + codec

Reads the live FightScene's logical fields into the frozen Snapshot shape each tick, encodes (JSON → binary → delta), ships it, and the guest applies it through an interpolation buffer.

→ Lessons 1 & 5 · snapshotCodec.ts, interpBuffer.ts
determinismHarness

The offline determinism analysis

Seeds the 3 RNG sites + a fixed timestep and proves same-seed → identical outcome headlessly, then scores how expensive full determinism would be.

→ Lesson 7 · determinismHarness.ts

3 The five pages

The app is a hash-routed dashboard (that's the #/home in your URL). Each experiment is one page, all built to the identical skeleton so learning one teaches the rest:

#/transport

Transport

WebSocket vs WebRTC RTT/jitter/loss. Sweeps loss settings, reports p50/p95/p99. The HOL-blocking test.

#/sim-snapshot

Sim-snapshot

Captures the real fight state, relays it, renders on a second client. Measures byte size & encode cost; surfaces the pose-fidelity gap.

#/e2e-remote-input

Remote input (E2E)

The decisive one: real fight, guest input over the wire, measures felt input lag vs the ~3-frame ceiling.

#/determinism-cost

Determinism

Offline. Proves reproducibility where cheap; prices the structural rewrite rollback would need.

#/summary

Summary

The honest composite: geometric-mean + min-gate, every sub-score with band/weight/rationale, feasibility and determinism on separate axes.

4 Running it: host + guest

The URL you opened — ?room=probe2&role=guest#/home — is the whole pairing model in three query params. Here's how a real two-machine run works:

  1. Machine A opens the host. Visit the app with ?room=myroom&role=host. The room is any shared id; role=host means "this browser runs the real sim."
  2. Machine B opens the guest. Same URL, same room, but ?role=guest. Matching room ids is how the server pairs the two into one session.
  3. They connect. Over /ws (WebSocket) or, for the WebRTC path, the /signal handshake opens a direct DataChannel (Lesson 3).
  4. Run an experiment. On any page, press its primary Run button. Both halves execute; the guest presses keys in its canvas, the host simulates, snapshots flow back.
  5. Read the result (next section), then hit the sidebar's Run all for the composite Summary.
Solo mode. Open with no ?room and the app runs both halves locally over a loopback pair with a simulated network — great for a demo, but the numbers are indicative only. That's why loopback runs wear an amber simulated network badge and a warning callout: a real WS-vs-WebRTC verdict needs two actual machines.

5 Reading a result

Every experiment renders the same result block, and the app's design philosophy is the "three-second page": glance and know what it measures, whether it ran, and if the answer is good or bad. What you're looking at:

  • Verdict strip — a status chip (completed/failed) + a one-sentence judgment + topology/loss chips.
  • Stat tiles — the decisive numbers (p50/p95/p99, byte size, felt lag) each with a Good/Acceptable/Bad band color. A red tile means bad; you can trust that without reading a word.
  • Details accordion — the full prose, sub-score rationale, caveats, raw tables. Collapsed by default (for the engineer-skeptic who wants to audit).
  • Mode badge — green real vs amber simulated: always check this before trusting a number.
reading tip

The colors are the message

The app is built so a non-technical teammate can glance at any page and read the traffic-light verdict correctly. As someone who now understands the internals, you get both layers: the band color for the instant read, and the accordion + raw cells to verify why. When in doubt, expand the details — every number's provenance is one click away.

The reframe that matters. The dashboard's headline — 49/100 "not feasible", min-gated by a bad ~7-frame input-lag score — is not decision-grade. That number came from a pessimistic default (80ms RTT = 2× the project's own target) measured over just 4–5 samples of a button-ack that never landed a hit (Lessons 6, 8). At target-consistent settings the (still simulated) felt lag is ~2–3.5 frames. The outlook shifts from "feared past the edge" to "the fear is largely an artifact — likelier to pass on real hardware than the red implied." The action doesn't change: measure first.

The robust findings (unchanged — and these are what actually support the decision):

  1. Snapshotting is bandwidth-cheap — tiny, near-free to encode (Lesson 5).
  2. ...but render is structurally lossy — the guest is a "teleporting puppet"; faithful pose needs a production state→render API (Lessons 1, 5).
  3. The input seam is clean — swappable entirely harness-side, zero src/ combat edits (Lesson 4).
  4. Rollback stays closed — the determinism retrofit is structural/expensive; host-authoritative wins on cost (Lesson 7).

Known issues & the refactor (in progress)

Since you're mid-refactor, here's the punch-list the reviews converged on — each item tracing to a lesson so you know why it matters:

measurement

Make felt-lag decision-grade

The one gating number needs: a presence barrier (don't drive until both peers are subscribed — today a host-drives-first run leaves a late guest hanging forever), an internal stall timeout, a clock offset feeding the interp sampler, a visibilitychange guard (a backgrounded tab's rAF throttling gave 466ms from 1 sample), a sample-count floor + hundreds of samples, and in-range inputs so a hit actually lands. → Lessons 5, 6, 8.

transport

Fair WS-vs-WebRTC

The in-app loss proxy can't reach the peer-to-peer leg, so the head-of-line comparison is structurally unfair. A real verdict needs an OS-level network conditioner on both legs. → Lesson 2.

connectivity

Add TURN + buffer ICE

STUN-only fails for symmetric/CGNAT users; add a config-injectable TURN server, and queue ICE candidates that arrive before setRemoteDescription. → Lesson 3.

deploy

Render build + cold-start UI

Copy render.yaml to the repo root; install the root phaser dep (the prod build depends on it); move tsx into dependencies; pin one instance (rooms are in-memory); and build the "waking server…" UI the free tier's spin-down needs.

stability

Tame WebGL context churn

Each E2E run spins up several throwaway Phaser.Games; Chrome caps live WebGL contexts (~16) and evicts the oldest, blanking a long-running canvas. Reuse one pair and/or use Phaser.CANVAS for offscreen measurement games.

Consolidated verdict (all passes): infrastructure-complete, evidence-incomplete. Keep host-authoritative; don't commit the track yet. Fix the paired measurement instrument, then take one trustworthy felt-lag reading on two real machines at 20–60ms RTT (interp swept), and add an OS conditioner on both legs for the transport question. Then re-read the verdict — every word of which you now understand.
