1 Why this comes first

Your spike is a networking experiment, but networking a game means synchronizing two copies of a simulation that is constantly stepping forward in time. If you don't have a crisp picture of how that simulation advances — the "game loop" — none of the netcode vocabulary (tick, snapshot, rollback, fixed timestep) will land.

🎬Analogy: A game is a flipbook that draws itself. Every fraction of a second it asks "what buttons are held? what should move? now draw it." A single-player game only has to flip its own book. Multiplayer means two people are flipping the same book and it has to stay on the same page.

2 The loop: input → update → render

At its heart, every real-time game runs one loop, forever, many times per second. Each pass through it is one frame:

Inputread buttons
→
Updateadvance the sim
→
Renderdraw the frame
↺
frames drawn: 0

Input reads the current state of the controls. Update (also called the simulation or "sim") applies the rules of the game: move fighters, apply gravity, resolve hits, tick down timers. Render draws the resulting world to the screen. Then it loops. In the browser this loop is driven by requestAnimationFrame, which fires once per display refresh — usually 60 times a second (60Hz), sometimes 120.

3 Ticks vs. frames

These two words get used loosely, but the distinction is the whole game:

TermWhat it countsTied to
FrameOne render to the screenThe monitor's refresh rate (60/120 Hz)
TickOne update of the simulationThe game's chosen sim rate

They're often the same number (one sim update per drawn frame), but they don't have to be. A game can render at 120fps while simulating at a steady 60 ticks per second, or the reverse. Networking cares almost entirely about ticks, because a tick is the unit of game state you might send across the wire. When your spike's snapshot carries a tick field, it's stamping "this is what the world looked like at simulation step N."

under the hood

Why decouple them at all?

If your simulation math is bolted to the render rate, then a player on a 144Hz monitor experiences different physics than one on 60Hz — gravity is applied more often, so they fall faster. Decoupling the sim to a fixed rate makes the game behave identically regardless of the screen. This is exactly the property multiplayer needs: two machines must agree on what happened, and they can't if the answer depends on each player's monitor.

4 Variable vs. fixed timestep

How much time should one update advance the world? Two philosophies:

⏱️ Variable timestep

Each update advances by however much real time has passed since the last one (the "delta", often written dt). Simple, always smooth — but every run is slightly different, because dt is never exactly the same twice.

🔒 Fixed timestep

Each update advances by a constant slice (e.g. exactly 1/60s), accumulating leftover time and running as many fixed steps as fit. Every run with the same inputs produces the identical result.

Press play and watch two balls cross the same distance. Both look fine — but only one is reproducible.

Fixed timestep (1/60s steps)
Both arrive together — but only the fixed one lands on the same pixel every single time.
Why you care for netcode: the advanced models (lockstep, rollback) require that replaying the same inputs gives a bit-for-bit identical result on both machines. That is only possible with a fixed timestep. A variable-timestep game is fundamentally non-reproducible, so those models are off the table until you convert it — which is precisely the "determinism cost" your spike measures.

5 Sim vs. render: the split that enables netcode

The most important structural idea for everything that follows: separate what is true (the simulation state — positions, health, timers) from how it's drawn (sprites, animations, particle effects). The sim is the authoritative data; render is a view of it.

Think of a chess game: the state is "white knight on f3" — a tiny fact you could text to a friend. The render is the carved wooden piece, the lighting, the little bounce animation when it lands. To sync a game across the network you only need to send the state; each machine can draw it however it likes.

This is the entire premise of "host-authoritative" netcode (Lesson 4): one machine runs the real sim, captures the state as a snapshot (Lesson 5), and ships just that small state to the other machine, which draws it. It only works cleanly if state and render are actually separable.

6 How your spike's game is built

Your fighting game runs on Phaser (a popular 2D web game framework). The spike's research notes verified some things about it that matter for everything ahead:

🔀
It uses a variable timestep. "All timers keyed on real delta, no tick counter." So the sim is not reproducible yet — rollback/lockstep would require introducing a fixed step first. (This is why the determinism experiment scores low.)
🎭
State and render are tangled. The notes found that "sim mutations trigger rendering as a side effect" (taking damage directly plays a hit animation), and pose/animation live in fire-and-forget Phaser tweens with no snapshottable state. So a second machine can capture the logical state (position, health) but can't perfectly reproduce the pose from state alone — the spike documents this as a real finding.
🧍
Position lives in a physics body. Canonical position/velocity live in a Phaser Arcade.Body; the countdown lives in a Phaser TimerEvent. These are the fields the snapshot has to read out each tick.

Hold these three facts. Every later lesson — and every verdict the spike reports — traces back to them.

✦ Takeaways

  • A game is a loop: input → update (sim) → render, running ~60×/second.
  • A frame is one draw; a tick is one sim update. Netcode is about ticks.
  • Fixed timestep makes runs reproducible; variable timestep does not. Reproducibility is the gate for rollback/lockstep.
  • Separating sim state from render is what makes it possible to ship a tiny snapshot across the network.
  • Your spike's game is variable-timestep with tangled state/render — the root cause of its determinism cost and its snapshot fidelity gap.
