1 What a snapshot is

A snapshot is the complete logical state of the game at one tick, packed into a small message you can send across the network. Not the pixels, not the animations — just the facts: where each fighter is, how much health they have, what state they're in. It's the "chess notation" idea from Lesson 1, made concrete.

📸Analogy: A film reel is 24 photos a second. You don't mail someone the movie theater — you mail the photos, and their projector recreates the motion. A snapshot is one photo of the fight's state; the guest's "projector" (its renderer) turns a stream of them back into a moving match.

2 Your spike's actual snapshot schema

This is the real Snapshot type from your spike's contracts.ts — the exact shape that goes on the wire each tick:

interface Snapshot {
  tick: number;              // which sim step this is
  hostTime: number;          // producer's clock (for timing)
  p1LastInputSeq: number;    // "I've applied your input up to #N"
  p2LastInputSeq: number;
  round: number;
  countdown: number;
  winner: 0 | 1 | 2;
  fighters: [FighterSnap, FighterSnap];  // one per player
}

interface FighterSnap {
  x: number; vx: number;        // position + horizontal velocity
  health: number; confidence: number; special: number;  // HUD meters
  state: "idle"|"walk"|"attack"|"block"|"hitstun"|"ko";
  facingRight: boolean;
  attackTimer: number; hitstunTimer: number; chargeMs: number;
}

That's the entire fight, per tick: two fighters × a dozen fields, plus a little match metadata. Notice what's not here — no sprites, no animation frames, no particle effects. Just numbers and a couple of enums. That's what makes it tiny.

the seq numbers

Why p1LastInputSeq matters

Each input the guest sends is numbered (seq). When a snapshot comes back saying p2LastInputSeq: 47, the guest knows "the host has processed my input up through #47." That's how the guest confirms its button presses landed — and it's the hook a fancier model would use to reconcile prediction. Sequence numbers are the quiet backbone of every netcode protocol.

3 The serialization ladder: JSON → binary → delta

  • JSON (~427B): human-readable, native to JavaScript, trivial to debug. The right first rung: prove the loop works before optimizing.
  • Hand-packed binary (63B): write each field into a raw byte buffer (a DataView) at fixed offsets. ~7× smaller than JSON.
  • Delta (~18–25B/tick): only send the fields that changed since the last snapshot. Between two ticks a fighter barely moves, so most of the packet is unchanged — skip it.
The counter-intuitive part: your research found binary is smaller but not faster to build — userland binary packing was measured 1.6–3.2× slower than native JSON, because browsers' JSON is heavily optimized C++. So binary wins on size (bandwidth), not CPU. You climb the ladder for bandwidth, not speed — and only as far as you need. For 2 players, even JSON fits under one network packet.

How small is small enough? Under one MTU (~1192B for a WebRTC unreliable channel — Lesson 3), so the whole snapshot rides in a single packet and can't be split into losable fragments. At 63B, your spike is comfortably under. Encode cost is a couple hundredths of a millisecond — the deployed build measures ~0.016ms/frame against a 16.67ms frame budget — effectively free (the exact figure drifts run to run; it's always ~1000× under budget).

4 The interpolation buffer

Snapshots arrive with irregular timing — network jitter means one is 12ms late, the next 4ms early. If the guest drew each the instant it arrived, fighters would stutter and teleport. The fix: the guest holds a small buffer of recent snapshots and renders a smooth path between them, deliberately a little behind real time.

time →
Blue = snapshots arriving (jittery). Red = what the guest draws (smooth, but behind).

The guest renders at the red marker, always trailing the newest blue snapshot by the buffer amount. This hides the jitter — the render is always interpolating between two snapshots it already has, so it never has to guess or stutter. Your spike uses a 50ms interpolation buffer.

It's like a video stream's few seconds of "buffering." A small delay you accept up front buys you smooth playback despite an uneven network. The tradeoff is right there: a bigger buffer is smoother but adds directly to how far behind the guest is.
field notes · from the refactor

Two ways an interp buffer bites back

1. It assumes snapshots arrive in order. The spike's sampler walked the list and stopped at the first future sample — fine over ordered TCP, but under an unreliable WebRTC channel (Lesson 2) snapshots can arrive out of order, so it must insert them sorted by tick/hostTime. Reordering is the price of the fast transport.

2. It's where cross-tab clock skew actually bites. The sampler decides "which two snapshots straddle now?" by comparing the guest's own performance.now() against the host-stamped hostTime. But per MDN, each tab has its own time origin — two tabs' performance.now() clocks differ by seconds and aren't comparable. So the gate can decide every snapshot is in the future (or past), attribute zero samples, and silently render nothing useful. (Subtle point a later review pinned down: the felt-lag subtraction is epoch-safe — both values use the guest clock — so the real fix is feeding the sampler a measured clock offset, not touching the timestamp math.)

5 Hitting the opponent where they were

That deliberate delay has a sharp consequence. Because the guest renders the past, the opponent it sees on screen is where they were ~one buffer-length ago — not where they are now. This is called the stale opponent problem, and it's the deep reason fighting games struggle with this model.

🥊
You see the opponent begin an attack. You react and block. But you were reacting to a stale position — on the host's authoritative timeline, they'd already moved. For a shooter, "server rewind" forgives this. For a fighting game's frame-perfect blocks and throws, being ~100ms behind can mean your correct read still loses.

Valve's Source engine famously runs a 66-tick sim but sends only 20 snapshots/second, so the guest interpolates ~100ms in the past (cl_interp 0.1). Shooters live with it; frame-1 fighting-game interactions can't. Your spike measured stale-opponent lag as roughly equal to the interpolation delay — a direct, unavoidable cost of smoothing.

6 The fidelity gap your spike found

Here's the most important spike-specific finding of this whole topic. A snapshot carries the logical state — but your game's visual pose (the exact animation frame, the tween mid-flight) isn't stored as data anywhere; it's a side-effect of calling sim methods. So the guest can reproduce the HUD perfectly but not the exact pose from state alone:

✓ Reproduces exactly

  • Position & velocity (x, vx)
  • Health, confidence, special meter
  • Logical state (idle/attack/block/hitstun/ko)
  • Round, countdown, winner

✗ Does NOT reproduce from state

  • Exact animation pose / tween position
  • Move identity (moveId) — not in the schema
  • Per-hit damage amounts
  • Particle/visual effects (fire-and-forget)

A later review put the fidelity gap even more bluntly: because the guest's SnapshotGuestScene.update() is empty, the guest never runs its own tweens or timers — it's a teleporting puppet that snaps between received states rather than animating between them. Faithful motion would need that production state→render path.

Why? Because in your Phaser game "pose/tweens are side-effects of private mutators" — there's no state → render path (Lesson 1). Faithful guest pose would need a production snapshot/state-render API added to src/. The spike is honest about this: it's documented as a finding, not silently patched. (It also caught a real bug in passing: Fighter.chargeMs is a dead field — the schema implies charge lives on the fighter, but it actually lives on the scene.)

The practical read: snapshotting is bandwidth-cheap but render-lossy. For a HUD-first fighting game, "lossy pose" may be perfectly acceptable — but it's a real decision, and now it's measured rather than assumed.

✦ Takeaways & sources

  • A snapshot is the logical fight state for one tick — numbers and enums, no pixels.
  • Climb the serialization ladder (JSON → binary → delta) for bandwidth; binary is smaller but not faster. Stay under one MTU.
  • The guest holds an interpolation buffer to smooth jitter — at the cost of rendering the past (stale opponent).
  • Your spike's snapshots are tiny (63B full / ~25B delta, ~0.016ms to build) but render-lossy: HUD reproduces exactly, exact pose does not.
