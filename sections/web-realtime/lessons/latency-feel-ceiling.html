1 Everything is frames

A fighting game runs at 60 frames per second, so one frame is 16.67ms. That's the natural unit for lag: divide any millisecond figure by ~16 and you get "how many frames behind" the player is. This single conversion is how pros and researchers actually reason about netcode feel.

🎞️Why frames, not milliseconds: "120 milliseconds" sounds abstract. "7 frames" is concrete — it's 7 chances to react that you've been pushed back. A move that's active for 3 frames and you're 7 frames behind? You literally cannot see it start in time to respond. Fighting games are decided in single-digit frames, so single-digit frames of lag is the whole ballgame.

Your spike bakes this in: "frames @60fps = 16.67ms/frame; ping ÷ 16 ≈ frames the netcode must hide."

  • ≤1 frame (~16ms): imperceptible. Feels offline.
  • ~3 frames (~48ms): the "feels offline" ceiling. Killer Instinct ships a fixed 3-frame buffer — this is the accepted edge of "still feels like a local match."
  • ≥6 frames (~100ms): uncomfortable rubber-banding. Reads stop landing; the game feels like it's fighting you.

Academic surveys agree: a design goal of <75ms, with performance dropping sharply past 75–100ms; ~60ms is a better target for fast games than the classic 100ms figure. The ~3-frame ceiling is the line your spike's verdict is measured against.

3 RTT is not felt lag

A crucial distinction people constantly get wrong. RTT (round-trip time / ping) is just the network portion — how long a message takes to go and come back. Felt input lag (button-to-photon) is the whole chain from your finger to a visible change, and the network is only one link in it:

input poll
network RTT
interp buffer
sim + render
VSync + display

Felt lag = input poll + network RTT + interpolation buffer + sim/render + VSync/display. RTT is one slice; the interp buffer (Lesson 5) and display pipeline add real time on top.

The honest caveat your spike states: a browser can't measure true glass-to-glass lag (that needs a photodiode on the screen, like an LDAT). What it can measure is simulated network + app-processing latency — comparative, not absolute. It captures the input's event.timeStamp → the committed change in the next requestAnimationFrame, and reports the whole distribution with that caveat attached. It never pretends a browser number is a hardware number.
field note · from the refactor

Backgrounded tabs lie about time

A paired run once reported 466ms felt lag from a single sample against a 1ms RTT. Cause: when a tab loses focus, browsers heavily throttle requestAnimationFrame (down to ~1Hz, or pause it) to save power — so the render loop that samples felt lag nearly stops, and the few readings it takes are wildly inflated. Any in-browser latency measurement needs a visibilitychange guard that refuses to trust numbers gathered while the tab was hidden. Combined with the per-tab clock-origin issue (Lesson 5), browser timing has real footguns — always report the sample count and the visibility state.

4 Why jitter hurts more than lag

Jitter is the variance in latency — not "how slow" but "how inconsistent." And it's more damaging than steady lag, because humans adapt to a constant delay but can't adapt to a random one.

A steady 80ms delay: you learn to press slightly early and it feels fine. But 40ms that randomly spikes to 80ms means your timing is never right — the same input lands differently each time. This is why your spike's research says to weight jitter heavily in scoring, and why TCP head-of-line blocking (Lesson 2) is so toxic: it doesn't raise your average latency much, it adds brutal spikes. 5 The input-delay buffer & symmetric delay

Two techniques that manage — not eliminate — lag, both present in your spike:

🎛️ Input-delay buffer

Deliberately delay applying an input by a few frames, giving the network time to deliver the matching remote input so both stay in sync. A knob: more buffer = smoother under jitter, but adds directly to felt lag. Your spike exposes this as a tunable slider so you can see the tradeoff live.

⚖️ Symmetric input delay

If only the guest is delayed, the match is unfair. The fix: delay the host's input by the same amount, so both players feel the identical delay. It converts an unfair asymmetry into a fair, even constant — a config change, not an architecture change.

Read at face value that's ~6.4–7.2 frames — band BAD, well past the ~3-frame ceiling, decomposing exactly as this lesson predicts: RTT + interp buffer + stale-opponent. That was the spike's original headline — "guest input lag is the wall." But two later reviews showed that headline is not decision-grade. It's faithful to the numbers on screen and wrong as a verdict, for three reasons:

🎚️
It's a config artifact. The default injects 80ms RTT — 2× the project's own 20–60ms target — plus the 50ms buffer. Since felt ≈ RTT + interp + ~10ms app, that default is practically engineered to land in the BAD band.
🔬
It's statistically hollow. Each run attributed only 4–5 samples, so p95 = p99 = max-of-5 — a tail over five points is noise (Lesson 2's sample-size rule).
🥊
It measures the wrong event. The E2E only ever sends a bare light:true edge with fighters ~320px apart vs a ~70px reach — so no hit ever lands. It's timing a button acknowledgement round-trip, not a real input→gameplay response.

The reconciled finding. Host-authoritative is being kept — nothing here reopens rollback. The felt-lag concern is real in principle (guest = RTT + interp + stale-opponent), but "the fear is largely an artifact": at the project's real target the (still simulated) number is ~2–3.5 frames — borderline-acceptable, more likely to pass on real hardware than the red dashboard implied. It changes the outlook, not the action — because the number simply isn't trustworthy yet. The one step every review converges on: fix the measurement instrument (presence barrier + stall timeout + clock offset + a visibilitychange guard + a sample-count floor + hundreds of samples + realistic inputs), then take one honest reading on two real machines at 20–60ms RTT.

✦ Takeaways & sources

  • Reason in frames: 16.67ms each; ping ÷ 16 ≈ frames behind.
  • The fighting-game feel ceiling is ~3 frames (~48ms). Past ~6 frames it rubber-bands.
  • RTT ≠ felt lag — felt lag adds input poll, interp buffer, render, and display on top. Browsers measure it comparatively, not absolutely.
  • Jitter (variance) hurts more than steady lag — weight it heavily.
  • The spike's ~7-frame "wall" turned out to be a config artifact (80ms RTT = 2× target) + a 5-sample measurement of a button-ack; at the 20–60ms target it's ~2–3.5 frames. Host-authoritative stands — but the number isn't decision-grade until the instrument is fixed.
