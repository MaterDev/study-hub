1 The two internet delivery models

Underneath every web connection is one of two "transport" protocols. They make opposite promises, and for a fast-twitch game the difference is everything.

📦 TCP — reliable & ordered

Guarantees every byte arrives, exactly once, in order. If a packet is lost, TCP re-sends it and holds back everything after it until the gap is filled. You never lose data — but you can be forced to wait.

✉️ UDP — fast & unordered

Fires each packet and forgets it. No re-sends, no ordering, no waiting. Packets can arrive late, out of order, or never. But a lost packet never delays the next one.

📚Analogy: TCP is a numbered book series you must read in order — if volume 3 is lost in the mail, you sit and wait for the reprint before touching volumes 4, 5, 6 (which are already on your shelf). UDP is a stack of daily newspapers: miss Tuesday's and you just read Wednesday's. For a game, yesterday's position is useless anyway — you want the newest, now.

2 What the browser actually gives you

Browsers don't let you open a raw UDP socket. You get two realistic options, and your spike pits them against each other:

A WebRTC DataChannel configured with {ordered:false, maxRetransmits:0} behaves like UDP: fire-and-forget. That's the config your spike labels webrtc-unreliable. WebRTC can also run a reliable-ordered channel (like TCP) — the spike uses a separate reliable channel just for match setup messages, and the unreliable one for the fast per-tick data.

note

Why WebSocket goes through a server but WebRTC is peer-to-peer

A WebSocket always connects a browser to a server — two browsers can't WebSocket to each other directly. So a WebSocket game relays every message through a middle server (an extra hop, extra latency). WebRTC's whole point is a direct browser-to-browser link with no relay in the middle — but setting that up is surprisingly involved, which is the entire next lesson (signaling).

3 TCP head-of-line blocking (the whole story)

This is the single most important idea in transport choice, and it has a name: head-of-line (HOL) blocking. Because TCP must deliver in order, one lost packet stalls every packet queued behind it until the lost one is re-sent — at least one full round-trip later. In a 60Hz stream of fighter positions, that's a visible freeze.

UDP delivers 1, 2, 4, 5, 6 immediately and simply never shows 3. For a fighting game, arriving-late-but-complete is worse than arriving-now-with-a-gap: the game only ever wants the freshest state.

4 Why the p99 tail decides it, not the median

Here's the trap your spike's research explicitly warns against. On a clean connection, WebSocket and WebRTC have nearly identical latency. If you benchmark them by average (mean) round-trip time, they look the same and you conclude "WebSocket is fine." That benchmark proves the wrong thing.

The cost of TCP only appears under packet loss, and only in the tail — the rare-but-brutal slow messages. That's why the spike reports percentiles, never means:

p50 (median)
the middle msg
p95
95% faster than
p99 (the tail)
the worst 1%

p99 means "99% of messages were at least this fast; 1% were worse." In a game running 60 messages a second, the worst 1% happens constantly — several times a second — and each one is a visible hitch. Your spike measured this directly: under 15% link-loss, WebSocket's tail blew out to p50 ~800ms / p99 ~1038ms — real TCP head-of-line blocking on the WS leg. (Unreliable WebRTC on a clean link sat near 0.56ms, but that is not an apples-to-apples comparison — see the fairness caveat in §6.) The median hid the WS catastrophe; the tail exposed it.

But a percentile is only as good as its sample count. A p99 computed over 10 messages is noise — one outlier is the 99th percentile. Rule of thumb: you want roughly 100+ samples before a p99 means anything, and thousands for a stable p99.9 (a heuristic from the percentile math, not a spec). The refactor flagged exactly this: the transport experiment sampled only ~10 per cell — enough for a p50, far too few for the p99 the verdict leans on. Print n= and suppress the tail when n is small.
The methodology rule: "A mean-RTT benchmark proves the wrong thing." Also: measure round-trip on one clock (RTT = now() − t0 on the sender) so you never have to sync two machines' clocks, and inject loss deliberately — on a clean LAN, loss ≈ 0 and you measure nothing.

5 link-loss vs. payload-drop

Your spike is careful about where it drops packets, because only one kind actually tests HOL blocking:

link-loss

Drops bytes below the TCP layer, in a proxy in front of the server. TCP sees a real gap and does its re-send-and-stall dance. This is the only mode that produces genuine head-of-line blocking — so only link-loss backs the WS-vs-WebRTC verdict.

payload-drop

Drops messages at the application layer (the client just ignores some). No HOL blocking — TCP never knows. Useful for testing how the game copes with missing snapshots, but it does not prove anything about transport choice.

Your spike's loss proxy (server/lossProxy.ts) sits on the public port and delays bytes per TCP connection — "real head-of-line blocking at the byte level, below WS frame parsing." Its self-check showed 20 round-trips averaging 0.2ms with loss off, jumping to 321.6ms (several trips >800ms) with 40% loss on — queued behind earlier delayed chunks, i.e. real HOL, not independent jitter.

field note · from the refactor

"open" doesn't mean anyone's there

A real bug caught in this spike's refactor: the guest tab saw its transport go open and charged ahead — but no host had actually joined. Why? A WebSocket's open event fires when the socket reaches the relay server, which happily seats a single lone peer. Per MDN, readyState === OPEN describes only the client↔server transport — it says nothing about an application-level peer being present. The lesson: transport-connected ≠ session-ready. You need an explicit app-level "peer joined" signal; a 15-second "did the peer arrive?" guard that keys off open will never fire, and the run stalls until it times out.

6 What your spike measures

The Transport experiment (the /transport page) exists to answer sub-question 1: does WebSocket-over-TCP deliver acceptable RTT/jitter/loss, or does WebRTC measurably beat it — on real cross-machine data?

  • Both a WebSocketTransport and a WebRTCTransport are built against one shared Transport interface (Lesson 9 covers this "swappable port" idea), so the same experiment runs on either.
  • It sweeps loss settings (0/0.5/1/2/5%…) and reports p50/p95/p99, jitter, and throughput — never means.
  • The verdict rests entirely on the loss-conditioned p99 tail. The research's honest going-in position: "WebSocket is probably fine for same-region; the WebRTC case rests entirely on loss-conditioned p99 — measure it, don't assume it."
Field note · from the refactor: a later review found the spike's WS-vs-WebRTC comparison is structurally unfair as built. The in-app loss proxy only fronts the server port (:8080), so the peer-to-peer WebRTC channel never passes through it — a "completed" run therefore compares WS-with-loss against WebRTC-with-no-loss. A fair head-of-line test needs an OS-level network conditioner on both legs (e.g. tc netem / Network Link Conditioner), not an app-layer proxy that one transport bypasses. Only the isolated loss-resilience sub-score is apples-to-apples today.
one more detail

TCP_NODELAY and Nagle's algorithm

TCP has a bandwidth-saving feature (Nagle's algorithm) that coalesces small, frequent messages into bigger ones before sending — great for file transfer, poison for a 60Hz game because it adds delay. Your server sets TCP_NODELAY to switch it off, so the WebSocket baseline isn't unfairly slowed vs. WebRTC's unbuffered channel. Fair benchmarks require killing this kind of hidden buffering.

✦ Takeaways & sources

  • TCP = reliable + ordered (can stall); UDP = fast + unordered (never stalls). The browser gives you WebSocket (TCP) and WebRTC DataChannel (UDP-like, configurable).
  • Head-of-line blocking is TCP's real cost: one lost packet freezes everything behind it for ≥1 round-trip.
  • It only shows up under loss, in the p99 tail — so benchmark percentiles, never means, and inject link-loss (below TCP), not payload-drop.
