What the browser is doing each frame
  • Your rAF callback fires — the timestamp argument is read from the high-resolution performance clock

  • requestAnimationFrame(tick) is called at the end — schedules the next callback before the next vsync

What's happening
  • Ball A: moves 2px per rAF callback. On 60Hz = 120 px/s. On 120Hz = 240 px/s. Under stress (every other frame delayed ~50ms) = ~50px/s — it slows down.
  • Ball B: moves 120 × dt / 1000 px. At 60fps dt≈16.67ms → 2px/frame. At 120fps dt≈8.33ms → 1px/frame. Same total speed.
  • Hit Stress to see them diverge — Ball A slows to a crawl, Ball B stays at 120 px/s regardless of frame timing.
  • In a real game or physics simulation, frame-rate dependence means different players on different hardware experience different game speeds — a serious bug.

Easing Lab

Six easing functions written in pure JavaScript. Each shows the mathematical formula, an SVG curve (the x-axis is time, y-axis is progress), and a ball preview. The same math underlies CSS cubic-bezier() and GSAP's easing system.

Simultaneous comparison — all 6 easing functions on the same track:
Reading the curve
  • X axis = time (t from 0→1). Y axis = output progress (also 0→1 for most functions).
  • A steep early slope means fast initial movement that slows down (easeOut). Flat start, steep end means slow start, fast finish (easeIn).
  • Elastic and bounce curves go above 1 — the output overshoots. With lerp(a, b, t) this means the animated value temporarily exceeds the target before settling.
  • All CSS timing functions (ease, ease-in-out, cubic-bezier) are approximating these same polynomial shapes with Bezier curves.

Canvas: Orbital Gravity Well

A canvas animation using everything from this lesson: an rAF loop, delta time for frame-rate independence, eased attraction toward the mouse, and fading trails. Each dot moves at a physically correct speed regardless of frame rate.

What's happening in the loop
  • Update: each dot calculates a vector toward the mouse and applies it as acceleration. Velocity is capped via lerp. All movements scaled by dt.
  • Trail: instead of ctx.clearRect each frame, we draw a semi-transparent black rect. Old frames fade slowly — producing a trail. The Trail slider controls the alpha (fade speed).
  • Dots: rendered with ctx.arc(). Color is mapped to speed — slow dots are blue/purple, fast dots shift to orange/red.
  • HUD: fps, dt, and dot count are shown in a DOM overlay (position: absolute over the canvas) — updated each frame via textContent, not ctx.fillText.
  • Move your mouse over the canvas — dots eased-attract toward the cursor position using the same lerp + easing math from Tab 3.
