Browser Rendering Pipeline

Observe the real cost difference between expensive and compositor-only animations.

Step 1 — Enable Paint Flashing in DevTools

Open DevTools (F12) → More tools → Rendering → check Paint flashing. Click Animate and watch the tracks. The left box has a gradient + box-shadow to make its repaint region larger and more visible. The right box uses will-change: transform so it gets its own layer — no paint flash at all.

💡 If flashing looks similar: use the Performance panel instead. Record while animating and compare the purple "Layout" bars in the flame chart — they only appear for the left box.

❌ Expensive left: 200px
Layout → Paint → Composite
left

Gradient + box-shadow makes the repaint region large and visible. Watch for the green flash covering the whole track.

  • Every frame, the browser recalculates the geometry of the entire page (Layout)
  • It then redraws the box's gradient and shadow into a bitmap (Paint) — this is what causes the green flash
  • Only then does it hand the result to the GPU (Composite)
  • On a complex page, Layout alone can take 5–10ms — eating most of your 16ms frame budget
✅ Performant transform: translateX()
Composite only
transform

Runs on the compositor thread. No paint flash — the box is on its own GPU layer.

  • The box was already painted once when the page loaded — that bitmap lives on the GPU
  • Each frame, the GPU simply repositions the existing texture — no Layout, no Paint
  • will-change: transform tells the browser to promote this element to its own layer upfront
  • This animation stays smooth even if your JavaScript is busy doing other work on the main thread

What is layout thrashing?

When you read a layout property like offsetWidth, the browser needs an up-to-date layout to answer you. If you've just written a style change, the browser hasn't recalculated layout yet — so it's forced to do it right now, synchronously, before returning your value. If you then write again and read again in a loop, you force a full layout recalculation on every single iteration. With 50 elements, that's 50 layouts per frame instead of 1.

❌ Thrashing — interleaved reads & writes
boxes.forEach(box => {
  // READ — browser must flush pending
  // style changes and recalculate
  // layout right now to answer this
  const w = box.offsetWidth;

  // WRITE — invalidates layout again
  box.style.width = w + delta + 'px';
  box.style.height = box.offsetHeight
                     + delta + 'px';

  // Next iteration: same thing again.
  // 50 boxes = 50 layout recalcs/frame
});
With 50 elements this forces ~100 layout recalculations per frame — each one potentially taking milliseconds. You will drop frames.
✅ Optimised — batch reads, then writes
// Phase 1: batch ALL reads
// Browser calculates layout once
const measurements = boxes.map(box => ({
  w: box.offsetWidth,
  h: box.offsetHeight
}));

// Phase 2: batch ALL writes
// No reads follow, so layout isn't
// forced to recalculate mid-loop
boxes.forEach((box, i) => {
  box.style.width  = measurements[i].w
                     + delta + 'px';
  box.style.height = measurements[i].h
                     + delta + 'px';
});
1 layout recalculation per frame regardless of how many elements. Frame time stays well within the 16ms budget.

🛠 DevTools tip

Run the thrashing version, then open the Performance panel and record for 2 seconds. In the flame chart, look for tall purple "Recalculate Style" and red "Layout" bars repeating inside each frame. Then do the same for the optimised version — you'll see those bars almost disappear.

Compositor layers — the good and the bad

When the browser promotes an element to its own compositor layer, it can move, fade, or transform that element entirely on the GPU without touching layout or paint. But each layer consumes GPU memory — and on mobile, over-promoting can be worse than not promoting at all. Below are four cards showing different promotion states, all animating the same way. ✅ Apply before, remove after
// Promote just before animation
el.style.willChange = 'transform';

animate(el, { x: 200 }, {
  duration: 400,
  onComplete: () => {
    // Release the layer when done
    el.style.willChange = 'auto';
  }
});
Layer exists only while needed. Memory freed immediately after.
❌ Promoting everything
/* Don't do this */
* {
  will-change: transform;
}

/* Or this */
.card {
  will-change: transform, opacity,
               left, top, width;
}
Every element gets its own GPU layer. On mobile this exhausts VRAM and causes crashes or severe jank.
