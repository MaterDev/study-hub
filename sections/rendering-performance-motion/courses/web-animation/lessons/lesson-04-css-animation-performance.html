The rendering pipeline

Every frame the browser renders follows the same sequence: Style → Layout → Paint → Composite. The trick is that you choose how far through that pipeline your animation travels — and the further left you go, the more expensive each frame becomes.

The 16ms frame budget

At 60fps, the browser has 16.67ms to produce each frame — from JavaScript through to pixels on screen. Every millisecond you spend in Layout or Paint is a millisecond stolen from the work budget. Exceed 16ms and a frame is dropped.

📐 Under the hood — what "paint" actually is

When the browser paints an element, it hands the draw commands to Skia (Chrome's 2D graphics library, also used in Android) which rasterizes the element into a pixel bitmap. That bitmap is then uploaded to the GPU as a texture. If you change background-color every frame, Skia rerasterizes and the GPU re-uploads that texture every frame — consuming upload bandwidth. With transform, the texture is uploaded once and the GPU compositor simply repositions it using a matrix multiply. No rasterization, no upload.

Main thread vs compositor thread

The real payoff of compositor-only animations isn't just speed — it's isolation. The compositor thread runs independently of the main thread. Even if your JavaScript is doing something expensive (parsing JSON, running a search algorithm), a transform animation won't stutter. It lives on a completely different thread.

The will-change property

will-change tells the browser to promote an element to its own GPU layer before the animation starts. This eliminates the first-frame hitch that would otherwise happen when the browser promotes the layer on-demand.

Here's what that layer tree looks like. Each promoted element occupies its own GPU texture:

GPU compositor layer tree
Page root ~800 KB root layer
.header ~48 KB position: fixed
.card (will-change) ~96 KB will-change: transform
.modal ~200 KB will-change: opacity
Total GPU memory: ~800 KB
⚠️ Layers cost GPU memory — don't overdo it

Every compositor layer is a separate GPU texture that lives in VRAM. Mobile devices share GPU memory with the display framebuffer. Promoting 30 cards to their own layers can consume 50–100MB of VRAM and slow things down on mid-range hardware. The browser may fall back to software compositing entirely.

  • Only promote elements that are actively about to animate
  • Add will-change in JS just before animation; remove on animationend
  • Never use will-change: all
// ✅ Add just before animation, remove after
el.addEventListener('mouseenter', () => {
  el.style.willChange = 'transform';
});
el.addEventListener('animationend', () => {
  el.style.willChange = 'auto'; // frees the layer
});
📐 Under the hood — the layer tree and transform matrices

The compositor maintains a list of (texture, matrix) pairs — each compositor layer is a texture, and each has a 4×4 transform matrix that says where to draw it. To move a layer with transform, the compositor just updates one number in that matrix — a trivial operation. To move something with left, the browser must recompute layout geometry for the element and everything affected by it, repaint to a bitmap, re-upload to GPU, and then composite. Same visual result, 100× the work.

🌐 Industry pulse — RenderingNG rewrites the pipeline

Chrome's rendering engine was rewritten in 2021 as RenderingNG. The pipeline is no longer strictly serial: compositing now happens before paint in some cases, and a threaded paint system means more work can happen off the main thread. In practice, some paint-heavy animations that would have janked in Chrome 90 may now be smoother in Chrome 120+. But the mental model still holds: avoiding pipeline stages is always better than offloading them. The DevTools panels work the same way regardless.

Layout thrashing

Layout thrashing is what happens when you interleave DOM reads and writes inside a loop — forcing the browser to flush its pending layout queue over and over instead of batching it into one pass. The code looks innocent; the Performance timeline looks catastrophic.

// ❌ Thrashing — one layout flush per element
boxes.forEach(box => {
  const h = box.offsetHeight; // READ → forced flush
  box.style.height = h + 10 + 'px'; // WRITE
});

// ✅ Batched — one flush total
const heights = boxes.map(b => b.offsetHeight); // all reads
heights.forEach((h, i) => {
  boxes[i].style.height = h + 10 + 'px'; // all writes
});

📐 Under the hood — dirty bits and lazy layout

When you set a layout property (style.width = '200px'), the browser marks that element "layout dirty" but doesn't immediately compute new geometry. It queues up dirty elements and processes them in a batch at the end of the current JS task — right before paint. This batching is almost always invisible to you. But offsetWidth says "I need the current computed width right now" — so the browser is forced to flush the dirty queue immediately to give you an accurate answer. If you then write another property and read again, you've forced a second flush. The pattern from fastdom: always do all your reads, then all your writes, never interleaved.

The contain property

contain is a containment hint that tells the browser an element's subtree is independent from the rest of the page. When an animation inside a contained element triggers layout, only that subtree is reflowed — not the entire document.

Page
Header
Navigation
Widget (animating)
Footer

Without contain: the widget's layout animation propagates a reflow to the entire page — header, nav, footer all get reflowed too.

.widget {
  contain: layout; /* reflow stays inside */
}

.offscreen-section {
  content-visibility: auto; /* skip rendering entirely */
  contain-intrinsic-size: auto 300px;
}
💡 content-visibility: auto — the biggest easy win

content-visibility: auto skips all rendering (style, layout, paint) for off-screen elements until the user scrolls near them. For long pages with animated cards, this can cut initial render time by 50–80%. It implicitly applies contain: layout paint style to off-screen elements. Add contain-intrinsic-size so the browser knows how much scroll space to reserve while the element is invisible.

Ship checklist

  • ✅ Only transform and opacity are animated — not left, width, background-color
  • ✅ Paint flashing shows no green flashes on compositor animations
  • ✅ Layers panel shows no unexpected layer promotions
  • ✅ will-change is scoped and removed after animation ends
  • ✅ No layout property reads interleaved with writes in animation loops
  • ✅ contain: layout applied to animated UI regions
  • ✅ prefers-reduced-motion is respected
  • ✅ Tested with CPU throttled 4× (mid-range mobile simulation)
/* Always include this */
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration:        0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration:        0.01ms !important;
  }
}

🔨 Practical: profile and fix a janky animation

  1. Open the lesson example. Run both the left and transform balls simultaneously.
  2. DevTools → Rendering → enable Paint flashing. Watch which track lights up green every frame.
  3. Open Layers panel. Identify which element got its own compositor layer and why.
  4. Performance tab → record 3 seconds → stop → zoom into one frame. Find the Layout/Paint entries from the left animation.
  5. Add will-change: transform to the bad ball's element. Re-record. Does a new layer appear? Did the Layout bar shrink?
  6. Now fix it properly — change left to transform: translateX(). Re-record. Compare before and after.
  7. Bonus: In the will-change explorer, promote 40+ elements simultaneously and watch the memory estimate climb.
