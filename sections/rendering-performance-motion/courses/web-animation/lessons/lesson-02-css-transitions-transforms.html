CSS Transitions & Transforms

The two CSS tools you'll reach for in almost every animation. Understanding them at a deep level — not just their syntax — is what separates polished motion from amateur work.

Why this matters

CSS transitions and transforms are deceptively simple on the surface. A few lines of code and things move. But if you've worked through Lesson 1, you know the browser has a cost model underneath — and transforms are at the foundation of that model for a specific reason. They're the one CSS concept that maps almost perfectly to how the GPU works.

Beyond performance, there's craft here. The difference between an animation that feels premium and one that feels cheap often comes down to how well you understand transform origins, coordinate spaces, and the subtle math of 3D. This lesson builds that foundation.

The mental model

Transitions: reacting to state change

A transition is not an animation you play. It's a rule that says: "whenever this property changes, interpolate smoothly between the old value and the new value instead of jumping." The browser handles the rest.

This is an important distinction. A transition is stateless — it has no concept of a sequence or a timeline. It just watches for changes and smooths them. You trigger it by changing state (via class toggle, hover, JS, etc.), and the browser does the interpolation.

Transforms: changing visual representation, not layout

A transform is an instruction to the GPU: take this element's already-painted bitmap and apply a mathematical operation to it before displaying it. Crucially, this happens after layout — the element still occupies the same space in the document flow. Its box model is unchanged. Neighboring elements don't move. The visual representation shifts, but the geometry doesn't.

The dashed outline is the layout box — it never moves. The "before" and "after" boxes never shift. Only the visual pixels relocate. This is why transforms don't cause reflow and can run entirely on the compositor thread.

This is why transforms are compositor-safe. The browser has already done the layout and paint work. A transform just tells the GPU to reposition, rescale, or rotate the texture it already has.

How it works

The transition properties

.element {
  /* Longhand — the four transition properties */
  transition-property:        transform, opacity;
  transition-duration:        0.3s;
  transition-timing-function: ease-out;
  transition-delay:          0s;

  /* Shorthand — property duration easing delay */
  transition: transform 0.3s ease-out, opacity 0.2s ease;
}

Timing functions — what easing really looks like

The timing function controls the pace of change across the duration — it's a curve from 0% to 100% progress. linear moves at constant speed. ease-out starts fast and decelerates, which is why it feels natural for things appearing on screen. Watch them all race across the same distance:

Live — easing comparison
All boxes travel the same distance in the same duration — only the pace differs
💡 Key insight

ease-out (fast start, slow end) feels most natural for UI motion because it mimics how objects decelerate in the physical world. ease-in (slow start, fast end) is jarring for entrances but good for exits — things leaving the screen should accelerate away. ease-in-out is smooth for continuous loops.

⚠️ Common mistake

Using transition: all 0.3s ease. It silently watches every CSS property for changes — including layout-triggering ones like width and height. It also prevents per-property timing. Always list properties explicitly: transition: transform 0.3s ease, opacity 0.2s ease.

The transform functions

Each transform function applies a different geometric operation. The ghost outline shows where the element actually lives in layout — transforms don't move that. Only the rendered pixels shift.

tx
translate(x, y)
Moves the element. No layout impact. The most common transform — pure compositor work.
sc
scale(x, y)
Resizes around the transform origin. scale(1) = unchanged, scale(2) = double, scale(0) = invisible.
ro
rotate(angle)
Rotates around the Z axis (2D). Use rotateX/Y for 3D. Angle in deg, rad, or turn.
sk
skew(x, y)
Shears the element. No individual property equivalent. Use sparingly — distorts text.

Individual transform properties (modern CSS)

Since 2022, all modern browsers support translate, rotate, and scale as standalone CSS properties — separate from the transform shorthand. This solves a long-standing problem: with the old transform property, adding a new transform function would overwrite any others set elsewhere (e.g. in a JS animation). Now you can compose them independently:

/* Old way — overwriting transforms fight each other */
.card { transform: translateY(-8px); } /* hover lift */
/* JS sets transform: rotate(5deg) → wipes out the translateY! */

/* Modern way — individual properties stack cleanly */
.card {
  translate: 0 -8px;   /* CSS hover owns this */
  rotate: 5deg;        /* JS animation owns this — no conflict */
  scale: 1.02;
}
/* Browser applies in fixed order: translate → rotate → scale → transform */

Transform order — the gotcha that trips everyone up

Here is the core rule: each transform in the transform shorthand tilts the coordinate axes for every transform that follows it. So the same two functions, in a different order, operate on different axes and end up in completely different places.

The clearest way to see it is to step through each one:

Second transform rotate(45deg) — rotates around the origin. X axis stays screen-aligned. Spins in its new position. translateX(80px) — moves 80px along the current X axis, which is now diagonal. Moves at 45° to the screen.

Two syntaxes, two different rules about order

This is where a lot of confusion lives, so it's worth being precise about the difference:

transform shorthand vs individual properties — how order works
transform shorthand
/* Order is YOUR choice */
.a { transform: translateX(80px) rotate(45deg); }
.b { transform: rotate(45deg) translateX(80px); }
/* .a and .b end up in completely different places */
✓ You can choose any order
✓ Needed when order matters to your design
✗ Easy to accidentally get wrong
✗ JS and CSS can conflict (overwrite each other)
individual properties
/* Order is LOCKED: translate → rotate → scale */
.a { translate: 80px 0; rotate: 45deg; }
.b { rotate: 45deg; translate: 80px 0; }
/* .a and .b are IDENTICAL — written order is ignored */
✓ CSS and JS can each own a property
✓ No accidental overwrites
✓ Predictable — always translate → rotate → scale
✗ Can't choose rotate-before-translate
Rule of thumb: use individual properties (translate, rotate, scale) by default — they're safer and composable. Switch to the transform shorthand only when you need a specific non-default order (e.g. rotate-then-translate).

Transform origin

Every transform has a pivot point — the one coordinate that stays nailed in place while everything else moves around it. By default it's 50% 50% (the element's center). The orange dot shows the pivot. Watch the same 45° rotation with nine different origins:

Live — same rotation (45°), nine different origins
The orange dot marks the pivot. Notice how top left feels like a door hinging, bottom center like a plant growing, and center is symmetrical.
.card {
  transform-origin: center center;   /* default */
  transform-origin: top left;        /* door-hinge effect */
  transform-origin: bottom center;   /* grow up from baseline */
  transform-origin: 0 0 200px;       /* 3D: X Y Z offset */
}

.scene { perspective: 600px; }
.card  { transform: rotateY(30deg); }

/* preserve-3d lets children exist in the same 3D space */
.scene { transform-style: preserve-3d; }

The back face needs to start already rotated 180°, facing away from the viewer. Think of it as placing the back face face-down against the front face. When we later rotate the whole card 180°, the back face will spin around and now face the viewer — showing correctly. Without this pre-rotation, both faces would show the same side during the flip. Without this, when the front face rotates past 90°, you'd see it mirrored from behind — the browser renders both sides of every element. backface-visibility: hidden tells each face: if you're pointing away from the viewer (past 90°), become invisible. Now watch the oscillation — exactly one face is always visible. The front shows until it passes 90°, then disappears, and the pre-rotated back rotates into view. This is the core of the illusion.

The final piece: a transition on the card's transform, and a .flipped class that sets rotateY(180deg). When the class is toggled, the CSS transition smoothly interpolates from 0° to 180°. Because both faces already have backface-visibility: hidden and the back is pre-rotated, the swap happens automatically at exactly the halfway point — no JavaScript needed for the visual effect.

🛠 DevTools — Animations panel

DevTools → More tools → Animations. Trigger any transition and it appears as a visual timeline. You can scrub through it, slow it to 0.1×, and inspect each property's easing curve. This is the fastest way to debug timing issues without touching code.

🛠 DevTools — Paint flashing

DevTools → More tools → Rendering → enable Paint flashing. Trigger a background-color transition and watch green flashes pulse every frame. Switch to transform and the flash disappears entirely — you've just moved to the compositor thread.

Forced layout during transitions

A transition does not prevent JavaScript from reading layout properties mid-flight. If you read offsetWidth from a transitioning element, the browser still performs a synchronous layout calculation to return an accurate value. In animation loops this causes layout thrashing — avoid reading layout properties inside requestAnimationFrame callbacks on transitioning elements.
