1 Where WAAPI fits

You have met CSS animations and transitions (declarative, but you can't reach in once they run) and requestAnimationFrame (total control, but you compute every frame yourself). The Web Animations API sits between them: the same keyframe-and-timing model CSS uses, available from JavaScript, returning an object you can control. MDN notes it also underlies CSS Animations and Transitions, so the two share one engine.

If you know the CSS vocabulary you already know most of the options. Tap a CSS term to see its WAAPI twin.

2 Your first animate()

element.animate(keyframes, options) creates an animation, starts it immediately and returns an Animation. Keyframes are an array of objects (or one object whose properties are arrays), and the second argument is either a duration in milliseconds or an options object. Change the controls: the box really animates, and the code underneath is exactly what runs.

The default easing is linear in WAAPI (CSS defaults to ease), a common first surprise. Pass at least two keyframes: a single one can throw in some browsers.

3 The Animation object: a playhead you control

What CSS can't give you is the return value. The Animation has a playhead (currentTime, in milliseconds), a speed (playbackRate) and transport methods: play(), pause(), reverse(), finish() and cancel(). Prefer updatePlaybackRate() to assigning playbackRate directly: it syncs the playhead first, so the speed change is smooth. reverse() flips the sign of the rate; after cancel() the animation is idle and you create a new one.

4 Timing and fill

Timing options shape the active part of the animation and what happens around it. delay waits before it starts, endDelay waits after it ends, iterations repeats it, direction can flip each pass, and iterationStart begins part-way in. The part people trip over is fill: what the element looks like outside the active period.

Each box animates from 100px to 200px and naturally sits at 0px. The dashed outline marks the first keyframe's position. Watch where each box sits during the delay (backwards) and after the end (forwards).

5 Sequencing with promises

Every animation has a finished promise that resolves when it completes and rejects if it is cancelled. That turns choreography into ordinary async code. There are also onfinish and oncancel callbacks, and a ready promise for when playback has actually started.

async function run() { await a.animate(kf, 600).finished; await b.animate(kf, 600).finished; // rejects if cancelled await c.animate(kf, 600).finished; }

6 Composite modes: layering animations

An element can carry several animations at once (el.getAnimations() lists them). By default the composite mode is replace: when two animations touch the same property, the later one simply overwrites the earlier one. With add, each builds on the last, so a translate and a rotate on transform combine. (accumulate is like add but merges values where it can: blur(2) and blur(5) become blur(7).) 7 Keeping the end state

When an animation ends, the element normally snaps back. fill: "forwards" holds the last frame, but it leaves a finished animation attached to the element, still consuming resources and outranking your normal CSS. MDN recommends against leaning on it. The clean way is to commit the final style, then cancel: commitStyles() writes the computed result into the element's style attribute. (persist() exists to stop the browser automatically removing a finished, replaced animation; replaceState reports active, persisted or removed.)

8 Off the main thread

The performance story has one rule: animations of properties the browser can composite, mainly transform and opacity, can run on the compositor thread, separate from the main thread that runs JavaScript, style, layout and paint. CSS animations and natively supported Web Animations typically get this treatment; a requestAnimationFrame loop never does, because it is JavaScript on the main thread. Anything that triggers layout or paint forces main-thread work. Try it: block the main thread for a moment and see who keeps moving.

9 Beyond time: scroll timelines and global control

Two last ideas. First, an animation's timeline doesn't have to be the document clock: pass a ScrollTimeline (or ViewTimeline) and scroll position becomes the playhead, with rangeStart and rangeEnd choosing where it applies. It is the JavaScript twin of CSS scroll-driven animation, and newer than the rest, so feature-detect it. Second, because every animation is an object, you can reach all of them: document.getAnimations() is a one-line way to honor a reduced-motion preference.

Scroll the box →
document.getAnimations().forEach(a => a.updatePlaybackRate(a.playbackRate / 2)); // and the preference itself: window.matchMedia('(prefers-reduced-motion: reduce)').matches

✦ Takeaways & sources

  • WAAPI is CSS's keyframe-and-timing model in JavaScript, with an Animation object you can control. Defaults differ: easing is linear, durations are milliseconds.
  • Control is the point: currentTime, updatePlaybackRate(), pause(), reverse(), finish(), cancel().
  • Fill and end states need care: prefer commitStyles() then cancel() over leaving fill: "forwards" attached.
  • finished is a promise that rejects on cancel, so sequences are plain await code.
  • Composite modes layer animations: replace overwrites, add and accumulate combine.
  • Compositor-friendly properties (transform, opacity) can animate off the main thread; a requestAnimationFrame loop never does.
  • Use CSS for simple state changes, WAAPI when you need runtime control, rAF for per-frame logic.
