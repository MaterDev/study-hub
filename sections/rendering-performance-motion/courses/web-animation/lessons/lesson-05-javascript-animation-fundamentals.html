Why requestAnimationFrame exists

CSS animation handles a surprising amount — smooth transitions, looping keyframes, even scroll-linked effects. But once animation logic depends on user input, physics, real-time data, or state that JavaScript already owns, you need to drive it from code. The question is: how?

The naive answers — setInterval, setTimeout — both get it wrong in ways that produce jank, battery drain, and animations that break at different screen refresh rates. requestAnimationFrame was designed specifically to fix those failures. Every JavaScript animation library you will ever use — GSAP, Framer Motion, Anime.js, Three.js, PixiJS — is built on top of it. Understanding rAF from first principles demystifies all of them at once.

This lesson builds a working animation engine from scratch. By the end you will understand the game loop, delta time, easing math, and how to start, stop, pause, and resume animations cleanly — with no library.

The mental model: frames and render loops

Your monitor refreshes at a fixed rate — typically 60Hz, sometimes 90Hz or 120Hz. Each refresh is a frame: the display hardware scans out a new image. If you want animation to look smooth, you need to update your scene once per frame, right before each scan-out.

A render loop is the pattern that makes this happen:

  1. Update — advance your animation state (move a ball, increment a counter, apply physics)
  2. Render — reflect that state in the DOM or canvas
  3. Repeat — schedule the next call

Game developers have used this pattern for decades — the "game loop" is one of the oldest patterns in interactive software. The web's version is requestAnimationFrame, which wires step 3 directly into the browser's rendering cycle. When the browser is about to paint a new frame, it calls your callback first, giving you a precisely-timed opportunity to update state before anything is drawn to screen.

💡 Key insight — rAF is a render hook, not a timer

requestAnimationFrame does not fire on a fixed millisecond interval. It fires once per browser render cycle, synchronized to the display's vsync signal. On a 60Hz display that's ~16.67ms; on a 120Hz display it's ~8.33ms. This distinction matters enormously: code running at 120Hz gets twice as many calls as code on 60Hz, so speed expressed in "pixels per frame" will be twice as fast. Delta time (covered below) is the solution.

The problem with setInterval

Before rAF existed, developers animated with setInterval(fn, 16). This seems reasonable — 1000ms / 60 = 16.67ms — but it fails in three ways:

  • Timer drift. setInterval fires based on the JavaScript event loop timer queue, which has no relationship to the display's vsync signal. Your 16ms interval and the 16.67ms frame boundary drift apart constantly, producing tearing and micro-jank.
  • Background tabs. setInterval keeps firing even when the page is invisible — wasting CPU, draining battery. rAF automatically pauses when the tab is hidden.
  • No timestamp. setInterval gives you no information about when exactly it fired. rAF passes a high-resolution timestamp, making time-based animation trivial.

📐 Under the hood — the vsync signal and display compositing

Modern displays use vsync (vertical sync) — a hardware signal that fires at the display's refresh rate and tells the GPU "I'm about to scan out a new frame, hand me the pixel data." The operating system's window compositor (Quartz on macOS, DWM on Windows, Wayland compositors on Linux) synchronizes with vsync so each frame appears cleanly without tearing. The browser hooks into this same signal: when the compositor is about to present a new frame, it notifies the browser's rendering engine, which runs rAF callbacks, then style/layout/paint/composite — all before the next vsync. This is why rAF callbacks are sometimes called "before-paint" callbacks. The requestAnimationFrame spec actually says the callback fires "before the next repaint" — vsync is the mechanism behind that.

The requestAnimationFrame loop

Basic structure

The minimal rAF loop looks like this:

function tick(timestamp) {
  // 1. Update state
  x += 1;

  // 2. Render
  el.style.transform = `translateX(${x}px)`;

  // 3. Schedule next call
  requestAnimationFrame(tick);
}

// Kick it off
requestAnimationFrame(tick);

The browser calls tick, tick schedules itself again, and this continues until you call cancelAnimationFrame on the returned handle. The callback receives a single argument: a DOMHighResTimeStamp.

DOMHighResTimeStamp

The timestamp passed to your rAF callback is a DOMHighResTimeStamp — a floating-point number of milliseconds since the page's time origin (roughly when the page started loading). It has sub-millisecond precision (typically microsecond resolution), and it is monotonically increasing — it never goes backward, even if the system clock changes.

function tick(now) { // 'now' is a DOMHighResTimeStamp
  console.log(now); // e.g. 4823.617 (ms since page load)
  requestAnimationFrame(tick);
}

You can also get the same timestamp at any point via performance.now() — the same clock, accessible anywhere.

Delta time — frame-rate independence

The loop above has a hidden bug: x += 1 advances by one pixel per frame. On a 60Hz display that's 60 pixels per second. On a 120Hz display it's 120 pixels per second — twice as fast. On a throttled laptop dropping to 30fps it's 30 pixels per second. Your animation speed is at the mercy of hardware.

The fix is delta time (dt): calculate how many milliseconds elapsed since the last frame, and express speed in pixels per millisecond instead of pixels per frame.

let prevTime = 0;

function tick(now) {
  const dt = now - prevTime;  // milliseconds since last frame
  prevTime = now;

  // ✅ frame-rate independent: speed in px/ms
  x += SPEED * dt;

  requestAnimationFrame(tick);
}
requestAnimationFrame(tick);

Now SPEED = 0.12 (px/ms) means 120 px/s on any display. A ball that takes 2 seconds to cross 240px will take the same 2 seconds whether the frame rate is 30, 60, or 120.

⚠️ Cap your delta on the first frame and after tab focus

On the very first frame, prevTime is 0 so dt will be something like 4800ms — the time since page load. After returning to a hidden tab, rAF was paused, so the first frame back might have dt = 3000ms, launching every object across the screen instantly. Cap it: const dt = Math.min(now - prevTime, 100). A 100ms cap means the maximum jump per frame is 10% of a second — invisible to the user, safe for physics.

📐 Under the hood — why this is the same problem as game physics

Game developers have wrestled with frame-rate independence since the 1980s. The classic fix is identical: express all motion in world units per second, multiply by the frame's elapsed time. A physics simulation running velocity += gravity * dt and position += velocity * dt is numerically solving differential equations using Euler integration — the simplest integration scheme in computational mathematics. It accumulates error over time (which is why game engines use more sophisticated integrators like Runge-Kutta for precise physics), but for visual animation, Euler integration with a capped delta is accurate enough and has negligible cost. The web animation stack is, in this sense, just a specialized physics simulation where the "physics" is aesthetic motion.

Easing functions from scratch

An easing function takes a progress value t from 0 to 1 (where 0 = animation start, 1 = animation end) and returns a transformed progress value that controls the pacing. Linear easing returns t unchanged — constant speed. Everything else accelerates, decelerates, overshoots, or bounces.

// t is progress from 0 to 1
const ease = {
  linear:    t => t,
  easeIn:    t => t * t,
  easeOut:   t => t * (2 - t),
  easeInOut: t => t < 0.5 ? 2*t*t : -1 + (4-2*t)*t,
};

// lerp is a separate utility — different signature, different role
const lerp = (a, b, t) => a + (b - a) * t;

Lerp (linear interpolation) is the fundamental tool: given a start value a, end value b, and eased progress t, it returns the value at that point between them. Combine lerp with any easing function:

const startX = 0, endX = 500;
const duration = 1000; // ms
let startTime = null;

function tick(now) {
  if (!startTime) startTime = now;
  const elapsed = now - startTime;
  const t = Math.min(elapsed / duration, 1); // clamp to [0,1]

  const easedT = ease.easeOut(t);
  const x = ease.lerp(startX, endX, easedT);

  el.style.transform = `translateX(${x}px)`;

  if (t < 1) requestAnimationFrame(tick);
}
requestAnimationFrame(tick);

Two of the curves above — elastic and bounce — behave differently from the others in an important way: they return values outside the range [0, 1]. Elastic overshoots (goes above 1.0 and briefly below 0.0), simulating the snap of a spring that stretches past its resting point before settling. Bounce stays within [0, 1] but oscillates against the target in a piecewise quadratic pattern — the mathematical equivalent of a ball hitting the floor multiple times with decreasing energy.

This matters in practice: if you feed an elastic t value directly into a position lerp, your element will briefly move past its destination and snap back. That's usually intentional (it's what gives elastic motion its physical, characterful feel), but you need to make sure the surrounding layout can accommodate it — an overshooting element can clip its container if overflow: hidden is set.

💡 These are the same curves as CSS cubic-bezier

The CSS timing functions you used in Lesson 3 — ease-in, ease-out, ease-in-out — are cubic Bezier curves that closely approximate these polynomial functions. The math underneath is the same. GSAP's Power1.out is easeOut, Power2.in is a cubic easeIn (t³). All roads lead back to the same arithmetic.

The game loop: start, stop, pause, resume

A production animation loop needs clean lifecycle management. The pattern below encapsulates everything: a handle for cancellation, a pause/resume mechanism, and a one-time start guard.

const loop = (function() {
  let rafId   = null;
  let paused  = false;
  let prevTime = 0;

  function tick(now) {
    if (paused) return;

    const dt = Math.min(now - prevTime, 100);
    prevTime = now;

    update(dt);
    render();

    rafId = requestAnimationFrame(tick);
  }

  return {
    start() {
      if (rafId !== null) return; // already running
      prevTime = performance.now();
      rafId = requestAnimationFrame(tick);
    },
    stop() {
      cancelAnimationFrame(rafId);
      rafId = null;
    },
    pause()  { paused = true; },
    resume() {
      paused = false;
      prevTime = performance.now(); // reset dt on resume
    },
  };
})();

Notice that resume() resets prevTime — otherwise the first frame after a long pause would have a massive delta. This is the same principle as the cap from the delta-time section, applied at the lifecycle level.

cancelAnimationFrame — cleaning up

requestAnimationFrame returns an integer handle. Pass it to cancelAnimationFrame to stop the loop. Always store and cancel the handle when a component unmounts or a modal closes — an orphaned rAF loop is a memory and CPU leak that will run forever.

// In a component teardown, event listener cleanup, etc.
const id = requestAnimationFrame(tick);

// Later, when you're done:
cancelAnimationFrame(id);
⚠️ The most common memory leak in JS animation

A rAF loop that schedules itself recursively and is never cancelled will run for the entire lifetime of the page — even after the UI it was animating has been removed from the DOM. In a single-page app where components mount and unmount, this compounds: each navigation that creates a new animation component without cancelling the old one's loop adds another perpetual rAF call. Profile it: DevTools → Performance → record → stop → look for CPU activity with no corresponding visible output.

Performance & debugging

What to keep out of your rAF callback

Your callback has a 16.67ms budget on a 60Hz display. Anything that runs over that budget causes a dropped frame. The most common offenders inside animation loops:

  • DOM reads that force layout — offsetWidth, getBoundingClientRect(), getComputedStyle(). If you need these values, read them before the loop starts, not inside it.
  • Heavy computation — physics for thousands of objects, pathfinding, sorting. Move this to a Web Worker or pre-compute it.
  • DOM writes that trigger layout — setting width, height, top, left. Use transform instead (Lesson 1/4 principle: compositor-only properties).
  • Texture uploads — creating new Image objects or large canvas operations inside the loop. Prepare assets outside.
🛠 DevTools tip — finding your rAF callbacks in the Performance panel

Open DevTools → Performance → Record while your animation runs → Stop. In the flame chart, look at the Main thread row. You'll see green bars labeled Animation Frame Fired — these are your rAF callbacks. Click one to see the exact JS call stack inside it and its duration. If your callback takes more than ~10ms, the remaining 6ms becomes too short for style/layout/paint and frames start dropping.

🌐 Industry pulse — rAF is the heartbeat of every major animation library (2024–2025)

GSAP 3's internal ticker runs a single master rAF loop and multiplexes every tween through it — never more than one rAF call regardless of how many animations are active. Framer Motion uses the same pattern via its internal frameloop package (also called @motionone/dom under the hood). Three.js, PixiJS, and Babylon.js all expose an animate() or render loop that wraps rAF. The shift toward single-ticker architectures (one rAF per page, not one per animation) became standard after 2020 when profilers showed that multiple competing rAF loops could cause subtle scheduling conflicts and higher CPU usage than a single orchestrator. Understanding raw rAF is the prerequisite for understanding why these libraries are architected the way they are.
