CSS Keyframe Animations

Where transitions end, keyframes begin. Multi-step sequences, fill modes, timing, staggering, play state control, and the new CSS scroll-driven animation API — all without a line of JavaScript.

Why this matters

TransitionsCSS transitions are reactive — they interpolate between two states when a CSS property changes (e.g. on hover). They can only describe A→B. They have no concept of looping, reversing, or multi-step choreography. are reactive — they respond to state changes. But what if you want an animation that plays on its own, loops forever, reverses on alternate iterations, or sequences through five distinct states? That's what @keyframes is for.

Keyframe animations are the backbone of CSS motion. Every loader, every entrance animation, every pulsing badge, every scroll-reveal effect relies on them. They're also the foundation for understanding how JavaScript animation libraries like GSAP and the Web Animations API think about motion — the vocabulary is the same even if the syntax differs.

And in 2023–24, CSS finally received scroll-driven animationScroll-driven animations link an animation's progress to a scroll position instead of time. As you scroll, the animation plays — with zero JavaScript. Uses animation-timeline: scroll() or view(). natively — no JavaScript scroll listeners, no IntersectionObserver boilerplate. This lesson covers the full picture.

The mental model

Keyframes as a storyboard

Think of @keyframes as a storyboard with named checkpoints. You describe what the element looks like at specific percentage positions along the animation's duration. The browser fills in everything between checkpoints by interpolatingInterpolation is computing the in-between values. At 50% between opacity: 0 and opacity: 1, the browser infers opacity: 0.5. Only interpolatable properties can be animated — transform, opacity, color, etc. Discrete properties like display can't be interpolated., using the same easing functions as transitions.

Live — playhead scrubs through five keyframe stops
box
The playhead moves from 0% → 100% over the duration. At each keyframe stop, the browser targets that state. Between stops, it smoothly interpolates. You can have as many stops as you need — not just from and to.
@keyframes slide-in {
  0%   { transform: translateX(-100%); opacity: 0; }
  60%  { transform: translateX(8px);    opacity: 1; }  /* slight overshoot */
  80%  { transform: translateX(-4px);  }               /* settle back */
  100% { transform: translateX(0);    }               /* final resting position */
}

/* from/to is shorthand for 0% / 100% */
@keyframes fade-out {
  from { opacity: 1; }
  to   { opacity: 0; }
}

/* Comma-group identical stops */
@keyframes pulse-border {
  0%, 100% { box-shadow: 0 0 0 0 rgba(91,138,245,0.7); }
  50%      { box-shadow: 0 0 0 12px rgba(91,138,245,0); }
}

The big difference from transitions: you control the entire sequence. A transition only knows State A and State B. Keyframes let you script any number of intermediate states, with different easing between each pair of stops, and the animation runs on its own without any triggering state change.

How it works

Attaching an animation — the shorthand decoded

.spinner {
  /* Shorthand — order matters for duration vs delay disambiguation: */
  /* name      duration  easing   delay   iterations direction fill-mode play-state */
  animation: spin        1s       linear   0s      infinite  normal    none      running;

  /* Duration always comes before delay when both are time values.
     The parser assigns the first time to duration, second to delay. */
  animation: spin 1s 0.5s;      /* 1s duration, 0.5s delay */
  animation: spin 1s 2 alternate; /* 1s duration, 2 iterations, alternate */

  /* Multiple animations: comma-separated */
  animation: spin 1s linear infinite, fade-in 0.3s ease-out both;
}

normal plays 0%→100% then resets. reverse plays 100%→0% — a mirror. alternate bounces back and forth smoothly — no reset at the loop point, which is why it's preferred for ambient loops. alternate-reverse starts from the end and alternates.

animation-fill-mode — the most misunderstood property

This is the single most common source of confusion in CSS animation. It controls what happens to the element before the animation starts (during the delay phaseDelay phase — the time between when the animation is applied (usually when a class is added) and when it actually begins playing. During this window, fill-mode controls whether the 0% keyframe has been applied yet or not.) and after it finishes. Without understanding fill-mode, your animations will inexplicably snap back to their original state.

Live — four fill modes with 0.7s delay, 1 iteration (watch the delay phase)
All four run the same animation with the same 0.7s delay. Watch during the delay: backwards and both immediately apply the 0% state. Then watch after finish: forwards and both hold the 100% state instead of snapping back.
💡 Key insight — fill-mode mental model

Think of fill-mode in terms of which keyframe the element "holds" outside the animation window. backwards = hold the from state during delay. forwards = hold the to state after finish. both = do both. none = snap back every time. In practice, use both by default — it eliminates both types of jarring jumps.

.element {
  animation: slide-in 0.4s ease-out 0.3s 1 normal forwards;
  /*                                              ↑
     forwards keeps the final (100%) state after finish.
     Without this, the element snaps back to its
     original position the moment the animation ends. */

  /* Most robust default: */
  animation-fill-mode: both; /* 0% during delay + 100% after finish */
}

animation-play-state — pausing without resetting

You can pause any running animation by setting animation-play-state: paused. Unlike removing the animation class, pausing preserves the exact current frame — the element doesn't jump. This is useful for hover effects, accessibility (respecting reduced-motion preferences), and manual scrubbing.

Interactive — click to pause/resume mid-animation
Pause the animation and notice the element freezes exactly where it is — not at 0% or 100%. Resume and it continues from that exact point. This is different from removing the animation, which would cause the element to snap back.
/* CSS approach — hover to pause */
.spinning-icon:hover {
  animation-play-state: paused;
}

/* JS approach — toggle with a class */
.paused { animation-play-state: paused; }

btn.addEventListener('click', () => {
  element.classList.toggle('paused');
});

/* Accessibility — respect user preferences */
@media (prefers-reduced-motion: reduce) {
  * { animation-play-state: paused !important; }
}

animation-delay — and the power of negative delays

Negative delay is one of the most useful tricks in CSS animation. animation-delay: -1s starts the animation already 1 second in — the element appears mid-animation, not at 0%. Combined with elements that all share the same keyframe, this makes them appear to be at different phases of the same cycle without any extra JavaScript.

Live — same keyframe, different delay offsets create a wave effect
All five circles run the same animation. Negative delays of 0, -0.4s, -0.8s, -1.2s, -1.6s put them at different points in the 2s cycle — creating a wave effect with a single keyframe.
@keyframes float {
  0%, 100% { transform: translateY(0); }
  50%       { transform: translateY(-20px); }
}

/* Wave effect: same animation, staggered by negative delay */
.dot { animation: float 2s ease-in-out infinite; }
.dot:nth-child(1) { animation-delay: 0s; }
.dot:nth-child(2) { animation-delay: -0.4s; /* already 0.4s into the cycle */ }
.dot:nth-child(3) { animation-delay: -0.8s; }
.dot:nth-child(4) { animation-delay: -1.2s; }
.dot:nth-child(5) { animation-delay: -1.6s; }
💡 Negative delay vs positive delay

Positive delay creates a gap before the animation starts (useful for entrance staggering). Negative delay skips the animation forward by that amount (useful for synchronized loops where elements need to appear offset in phase). Combine both: -1.5s with fill-mode: both means the element appears immediately at the 1.5s mark, with no delay.

Per-keyframe easing — a subtle but powerful feature

You can specify a different timing functionTiming function controls the rate of change over time. ease starts slow, speeds up, slows at end. linear is constant speed. ease-in starts slow (accelerates out). ease-out starts fast (decelerates in). cubic-bezier() gives full control. for each individual segment between keyframe stops. The easing you set inside a keyframe controls the transition from that stop to the next one.

@keyframes bounce {
  0%  { transform: translateY(0);    animation-timing-function: ease-in; }
  /* ↑ ease-in controls 0%→50% segment (accelerates upward, as gravity decelerates) */
  50% { transform: translateY(-60px); animation-timing-function: ease-out; }
  /* ↑ ease-out controls 50%→100% segment (decelerates as it falls and hits ground) */
  100%{ transform: translateY(0); }
}

/* The global animation-timing-function sets the default for all segments.
   Per-keyframe values override it for their own segment only. */
Live — per-keyframe easing: ease-in up, ease-out down
ease-in on the rise (slowing as it reaches peak — fighting gravity) and ease-out on the fall (accelerating downward — gravity taking over) produces physically convincing bouncing. A single ease or linear for the whole animation would look mechanical.

Timing function reference

Every animation property and transition uses a timing function. The built-in keywords are shortcuts for specific cubic-bezier() values. Understanding what each looks like is essential for choosing the right feel.

/* Built-in keywords and their cubic-bezier equivalents */
ease        /* cubic-bezier(0.25, 0.1, 0.25, 1)   — default, natural feel */
ease-in     /* cubic-bezier(0.42, 0, 1, 1)         — slow start, fast end */
ease-out    /* cubic-bezier(0, 0, 0.58, 1)         — fast start, slow end */
ease-in-out /* cubic-bezier(0.42, 0, 0.58, 1)      — slow both ends */
linear      /* constant velocity — mechanical, rarely desired */

/* Custom curves — P1 and P2 are the two Bézier control points */
cubic-bezier(0.34, 1.56, 0.64, 1) /* spring — overshoots then settles */
cubic-bezier(0.87, 0,    0.13, 1) /* sharp in-out — cinematic */

steps() — discrete animation

steps(n) divides the animation into n equal discrete jumps instead of continuous interpolation. The browser never shows the in-between state — it teleports from position to position. This enables two important techniques:

  • Sprite sheet animation — advance through frames in a sprite image without visible sliding between frames
  • Mechanical/retro motion — counters, clocks, anything that should tick rather than flow
Live — steps() vs linear: same distance, same duration
linear — smooth
steps(8) — discrete
steps(3)
The steps(n) function skips all intermediate values — the element teleports between positions. steps(3) shows how chunky the jumps get with fewer steps. See the jump-term note below for how start vs end affects which boundary each step lands on.
/* Sprite sheet animation — advance through 8 frames in a 800px-wide strip */
.sprite {
  width: 100px;
  background: url(sprite.png) left center;
  animation: walk 0.8s steps(8) infinite;
}
@keyframes walk {
  from { background-position: 0px; }
  to   { background-position: -800px; }  /* 8 frames × 100px */
}

/* jump-term: WHERE in each interval the jump occurs
   steps(n, end)   — default — jump at END of interval (frame shows for full step duration)
   steps(n, start) — jump at START of interval (first frame is immediately skipped)
   steps(1, end)   — one jump at the very end of the duration */

Staggering — cascading delays

The most ubiquitous animation pattern in UI is staggering: a group of elements that animate in sequence with small delays between each one. The technique is simple — each element gets a slightly longer animation-delay. The CSS calc() function with custom propertiesCSS custom properties (aka CSS variables) can be set per-element with inline styles and read in animation shorthand with calc(). This enables declarative per-element delay without any JavaScript — just set style="--i:3" and use calc(var(--i) * 80ms) as the delay. makes this elegant in pure CSS.

Live — staggered entrance, 90ms delay increment per element
Each bar has animation-delay: calc(var(--i) * 90ms) where --i is its index. The CSS calc() function reads the custom property and computes the delay declaratively — no JavaScript needed for the delays themselves.
/* In CSS: use custom properties set inline */
.item  { animation: fade-up 0.4s ease-out calc(var(--i) * 80ms) both; }

/* In HTML — the delay per element is purely data, not logic: */
<ul>
  <li style="--i:0">Item 1</li>
  <li style="--i:1">Item 2</li>
  <li style="--i:2">Item 3</li>
</ul>

/* Or in JS when the list is dynamic: */
items.forEach((el, i) => {
  el.style.setProperty('--i', i);
  /* or: el.style.animationDelay = i * 80 + 'ms'; */
});

animation-composition — stacking animations

✦ Modern CSS (2023+)

animation-composition controls how an animation value combines with the element's existing style or other running animations. The default replace overwrites completely. add stacks on top — a hover animation can add a lift to an already-running pulse without conflict. accumulate goes further and combines values mathematically (e.g. two rotate(45deg) animations → rotate(90deg), not rotate(45deg) rotate(45deg)).

.card {
  animation: pulse 2s ease-in-out infinite;
}
.card:hover {
  /* Two animations: pulse continues, lift adds on top */
  animation: pulse 2s ease-in-out infinite, lift 0.2s ease-out forwards;
  animation-composition: replace, add;
  /* 'replace' for pulse (default), 'add' for lift —
     lift translates on top of whatever pulse is doing */
}

Partial keyframes — starting from current state

✦ Modern CSS — partial keyframes

You can omit the from block, and the animation will start from the element's current computed stateComputed state — the resolved value of a property after applying the cascade (all stylesheets, inline styles, inherited values). At the start of an animation with no from block, the browser captures this value and uses it as the animation's implicit start point.. This is extremely useful for interruptible animations — if you add a class while another animation is mid-flight, the new animation picks up from wherever the element currently is rather than snapping to a defined start position.

/* Omit 'from' — starts from wherever the element currently is */
@keyframes slide-out {
  to { transform: translateX(100%); opacity: 0; }
}

/* If .modal is currently at translateX(-20px) due to a prior animation,
   slide-out picks up from -20px — no snap to 0. */
.modal.closing {
  animation: slide-out 0.3s ease-in forwards;
}

Scroll-driven animation — CSS only, no JavaScript

One of the most significant additions to CSS in recent years. animation-timeline: scroll() links an animation's progress to a scroll container's position — as you scroll, the animation plays forward. animation-timeline: view() ties the animation to the element's own visibility in the viewport.

💡 Browser support

Fully supported in Chrome 115+, Edge 115+, and Safari 26+. Firefox has it behind a flag. Use @supports (animation-timeline: scroll()) for progressive enhancement — non-supporting browsers just see no animation, which is an acceptable fallback for decorative motion.

/* Scroll progress bar — tied to root scroller */
.progress-bar {
  position: fixed; top: 0; left: 0; height: 3px;
  transform-origin: left;
  animation: grow-x linear;
  animation-timeline: scroll();       /* nearest scrolling ancestor */
  animation-range: 0% 100%;          /* full scroll range */
}
@keyframes grow-x {
  from { transform: scaleX(0); }
  to   { transform: scaleX(1); }
}

/* View timeline — plays as element enters viewport */
.card {
  animation: reveal linear;
  animation-timeline: view();             /* tied to this element's visibility */
  animation-range: entry 0% entry 40%;   /* plays as card enters viewport */
}
@keyframes reveal {
  from { opacity: 0; transform: translateY(30px); }
  to   { opacity: 1; transform: translateY(0); }
}

/* Named scroll timelines — for non-ancestor scroll containers */
.scroll-container { scroll-timeline: --my-scroller block; }
.animated-child   { animation-timeline: --my-scroller; }
Interactive — scroll the box to trigger reveals
In production this would use animation-timeline: view() — zero JavaScript. This demo uses IntersectionObserver as a polyfill for this embedded context. The principle is identical: each card triggers as it enters the viewport.

Performance & debugging

The same rules as transitions — property cost matters

Keyframe animations live in exactly the same rendering pipelineRendering pipeline — Style → Layout → Paint → Composite. Animations that only change compositor-layer properties (transform, opacity) skip Layout and Paint entirely and run entirely on the GPU thread — smooth even under main-thread load. Properties that trigger Layout (width, height, top) are expensive every frame. as transitions. The property you animate determines the cost:

  • transform and opacity — compositor only. Run on the GPU, bypass JS, stay smooth even when main thread is busy. Always prefer these.
  • background-color, box-shadow, filter — trigger paintPaint — the stage where the browser fills in pixels. Box shadows, gradients, color changes all require re-painting the affected area each frame. Visible as green flashes in DevTools → Rendering → Paint Flashing. every frame. Visible in DevTools paint flashing. Use sparingly.
  • width, height, top, left — trigger layoutLayout (also called Reflow) — the browser recalculates the position and size of every affected element. Changing width/height triggers layout for the element and potentially all its ancestors and siblings. This happens every frame if you animate these properties — extremely expensive. every frame. Extremely expensive. Always substitute transform: scale() or translate() instead.
⚠️ Common mistake — animating width or height

It's tempting to animate height: 0 → auto for accordion reveals. This triggers layout every frame. The modern approach: animate clip-path instead (compositor-safe, doesn't affect layout). Or use the WAAPI auto keyword (Lesson 6). For simple cases, max-height works as a workaround — still triggers layout, but often fast enough at short durations.

will-change — use it surgically

Adding will-change: transform before a heavy animation promotes the element to its own compositor layerCompositor layer — a separate GPU texture for an element. Changes to the element (transform, opacity) can be applied on the GPU without re-painting or touching the main thread. Creating too many layers wastes GPU memory — each one is a separate bitmap in VRAM., preventing it from triggering repaints on surrounding content. But every promoted layer costs GPU memory — never leave will-change on permanently in CSS. Set it just before the animation starts and remove it in the animationend callback.

/* ✗ Don't: always-on will-change in CSS */
.card { will-change: transform; } /* GPU memory wasted even when idle */

/* ✓ Do: add just before, remove just after */
el.addEventListener('mouseenter', () => {
  el.style.willChange = 'transform';
});
el.addEventListener('animationend', () => {
  el.style.willChange = 'auto'; /* release the layer */
});

/* For infinite animations, will-change can stay on —
   the layer is always in use. But audit with DevTools first. */
🛠 DevTools — Animations panel

Open DevTools → More tools → Animations. Trigger any CSS animation and it appears as an interactive timeline. You can scrub it frame by frame, slow it to 0.1×, inspect the easing curve, and change playback speed. This is the fastest way to debug timing — you don't need to edit code to understand what's happening at 60% of an animation.

🛠 DevTools — Performance panel

Record a Performance trace while an animation runs. Look at the Frames row — green bars are compositor-driven (fast), orange means the main thread was involved (risky). Any animation that touches width, height, top, or left will show as orange tasks in the main thread lane. The Animations panel + Performance panel together give the complete debugging loop.

🛠 DevTools — Layers panel

More tools → Layers. Drag to inspect which elements have been promoted to compositor layers. A well-optimised animation should promote only the elements that are actually animating. If you see dozens of unexpected layers, you likely have will-change leaking or a transform on a container that's promoting its entire subtree.
