Cluster 1 · Core Web Vitals

The Three Vitals

LCP, INP, and CLS are the three numbers that define "fast" for the modern web — and the shared vocabulary you'll use with your team, your stakeholders, and your browser's diagnostic tools.

⏱ ~20min · Beginner · Practice examples →

Why This Matters

Performance is a vague word. "Make it faster" is impossible to act on. The Core Web Vitals exist to give the industry three specific, measurable, user-centric signals that answer one question: what does this page feel like to use?

As a UI engineer, you'll encounter these metrics in Lighthouse reports, Google Search Console, DevTools, your analytics dashboards, and conversations with PMs. They're also a direct Google ranking factor — meaning a page's visual experience now affects its discoverability. Understanding what each one measures, and why, is the prerequisite for everything else in this workshop.

🔍The Key Idea

All three vitals are measured from real users in the field — not from a controlled lab. They capture what happens on slow phones, congested Wi-Fi, and low-memory devices. Your local experience is almost always best-case.

The Three Vitals at a Glance

Each vital guards a different dimension of experience: loading, interactivity, and visual stability. A page can excel at two and fail hard at the third.

LCP — Largest Contentful Paint

LCP answers: "When does the user see the main thing?" The browser continuously watches which element is the largest visible content on screen, and records the timestamp when it finishes painting. That timestamp is your LCP score.

What qualifies as an LCP element?

The browser considers these candidate elements: <img> elements, <image> inside SVG, <video> poster images, block-level elements with a CSS background-image, and block-level text elements (headings, paragraphs). The largest candidate by rendered area wins.

⚠️Common Mistake

Your LCP element is almost never what you think it is. Run a Lighthouse trace or open the Performance panel in DevTools — Chrome will highlight the actual LCP element. Many teams optimise the wrong image entirely.

The four phases of LCP

LCP isn't a single number to optimise — it's a waterfall of four distinct phases. You need to diagnose which phase is slow before you know what to fix.

  1. 1

    Time to First Byte (TTFB)

    The server's response time. If this is slow, DevTools alone can't fix it — you need CDN caching, faster database queries, or edge infrastructure. The browser can't start doing anything until bytes arrive.

  2. 2

    Resource Load Delay

    The gap between the HTML arriving and the browser discovering the LCP resource. If your hero image is injected by JavaScript or buried deep in a CSS file, the browser won't know to fetch it immediately. Fix with <link rel="preload"> in the <head>.

  3. 3

    Resource Load Time

    How long the actual download takes. Fix with compression (WebP/AVIF formats), responsive srcset so mobile users don't download desktop-sized images, and a CDN close to your users.

  4. 4

    Element Render Delay

    The asset has downloaded but the browser is blocked from painting it — usually because render-blocking JavaScript is executing or a large CSS file is still being parsed. Defer non-critical JS, inline critical CSS.

Under the Hood

Why "largest" is a heuristic for "most important"

The browser can't read your mind about what content matters. Using visual area as a proxy for importance is a deliberate engineering tradeoff. Empirical studies by Google found that the largest visible element correlates strongly with what users perceive as the "main content" — it's almost always a hero image, title, or above-the-fold article text. It's not perfect (a large background block would technically qualify), but it's accurate enough to be a reliable signal across millions of diverse pages.

INP — Interaction to Next Paint

INP answers: "When the user does something, how quickly does the page respond?" It replaced FID in March 2024 because FID was fundamentally incomplete: it only captured the first interaction ever, and it ignored the time spent actually running your JavaScript.

What INP actually measures

INP watches every click, tap, and keypress during a user's session. For each interaction it measures the full latency — from the moment the user acts to the moment the browser paints the visual response. At the end of the session, INP reports the worst interaction (with a small statistical buffer to ignore genuine outliers like accidental misclicks).

Phase 1
Input Delay
Time before the event handler even starts. Grows when the main thread is busy with another task.
Phase 2
Processing Time
Time spent running your event handler code. A slow handler here is code you wrote — long loops, heavy computation, synchronous DOM reads.
Phase 3
Presentation Delay
Time for the browser to recalculate styles, layout, paint, and composite after your handler runs. Triggering layout here is expensive.
💡DevTools Pro-Tip

In the Chrome Performance panel, click any interaction in the Interactions track. You'll see a tooltip breaking it into exactly these three phases — input delay, processing time, and presentation delay — with millisecond measurements for each. That breakdown tells you exactly which phase to fix.

Why FID was inadequate

FID had two crippling blind spots. First: it only measured the first interaction. If your page felt snappy on first click but then ground to a halt on the third, FID reported a passing score. Second: FID only measured input delay — the wait before your handler started — but completely ignored how long your handler took to run and how long rendering took afterwards. INP closes both gaps.

Computer Science Tangent

The main thread is a single-lane road

JavaScript is single-threaded by design — a decision made in 1995 to keep the language accessible and avoid concurrency bugs in UI code. The browser's main thread runs JavaScript, handles events, calculates CSS styles, performs layout, and paints — all in one lane. When a long JavaScript task occupies that lane, every queued interaction has to wait in line. This is the root cause of high INP scores in complex web apps. The fundamental fix isn't "write faster JS" — it's breaking long tasks into smaller pieces so the browser can service input events between them. We'll go deep on this in Cluster 4.

CLS — Cumulative Layout Shift

CLS answers: "Does the page move around unexpectedly while I'm trying to use it?" It's the metric that captures the experience of going to tap a button and having it jump away right before your finger lands — or starting to read a paragraph and having the text push down because an ad loaded above it.

How the score is calculated

Each layout shift gets an individual score: impact fraction × distance fraction. The impact fraction is what percentage of the viewport was disturbed. The distance fraction is how far the unstable elements moved, as a proportion of the viewport's largest dimension.

Individual shift scores are grouped into session windows. The CLS score is the worst session window — meaning a single burst of bad shifts at any point in the session can define your score, even if everything else was perfect.

The most common culprits

As a UI engineer these are the patterns you'll most commonly need to fix:

  • Images without explicit dimensions — the browser can't reserve space until the image loads, so surrounding content moves. Always set width and height attributes on <img> elements.
  • Ads, embeds, and iframes without reserved space. Late-loading third-party content is a major CLS offender.
  • Font swap (FOIT/FOUT) — when a fallback font renders at a different size than the final web font, text reflows and pushes other content. Use font-display: optional or size-adjust to match metrics.
  • Dynamically injected content — banners, cookie notices, chat widgets — inserted above existing content without pre-reserved space.
  • Animations that trigger layout — animating top, left, height, or width affects layout and can contribute to CLS. Use transform instead.
Under the Hood

What "layout" means in the browser pipeline

Every time a geometric property changes — width, height, position, margin — the browser must re-run its layout algorithm (sometimes called reflow) to recalculate where every affected element sits on the page. This is computationally expensive and propagates up the DOM tree. Layout shifts happen when this recalculation moves elements the user didn't expect to move. The browser distinguishes between expected shifts (like a navigation drawer opening in response to a click) and unexpected ones — CLS only penalises unexpected shifts that happen within 500ms of no user input.

The 75th Percentile Rule

Every Core Web Vital is evaluated at the 75th percentile of page loads — meaning your score represents what the bottom quarter of your users experiences. A page passes "Good" for LCP only if at least 75% of real users see LCP under 2.5 seconds.

At the 75th percentile: most users are in the green zone, but the slowest 25% define your pass/fail status. Optimising for the median alone misses the users who matter most.

The choice of 75th percentile is deliberate: the median (50th) would ignore too many real bad experiences, while the 95th would be so demanding that only the most engineering-heavy products could pass. The 75th catches the long tail without requiring perfection.

💡Field Data vs Lab Data

Your Lighthouse score (lab data) runs once, on your machine, on a simulated network. The CrUX field data that Google actually uses comes from a 28-day rolling window of real Chrome users. These two numbers will never match perfectly — and that's expected. We'll cover the difference in detail in Lesson 1.5.

Measuring All Three in Code

Google's web-vitals library (v4.x) makes it straightforward to capture all three metrics in real user sessions and send them to your analytics pipeline.

JavaScriptimport { onLCP, onINP, onCLS } from 'web-vitals';

// The callback fires when the metric value is "final" —
// LCP fires on page hide, INP on page hide, CLS on page hide.
onLCP(metric => {
  // metric.value: score in milliseconds
  // metric.rating: 'good' | 'needs-improvement' | 'poor'
  // metric.attribution: which element, which phase was slowest
  analytics.send('lcp', metric);
});

onINP(metric => {
  // metric.attribution.interactionTarget: CSS selector of the
  // element that triggered the worst interaction
  analytics.send('inp', metric);
});

onCLS(metric => {
  analytics.send('cls', metric);
});
✅Best Practice

Always capture metric.attribution, not just the score. Attribution tells you which element caused the slow LCP or INP — the CSS selector, the interaction type, the phase breakdown. A dashboard reporting "INP is 450ms" is unhelpful. "INP is 450ms on .mega-menu-trigger on mobile devices" is an actionable bug report.

In the Wild

Industry Context · 2026

Only 56% of sites pass all three — and INP is the hardest

As of the May 2026 Chrome UX Report, 55.9% of tracked origins pass all three Core Web Vitals simultaneously. CLS has the highest pass rate (81.3%) — most teams have learned to set image dimensions. LCP is middle ground at 68.6%. INP remains the most challenging at 86.6% passing — but that still means 43% of complex, interactive web apps are failing their responsiveness metric. For UI-heavy applications with large React trees, complex state, and third-party scripts, poor INP is the norm, not the exception.

Google's March 2026 core algorithm update confirmed that Core Web Vitals now carry equal ranking weight across all three metrics, and shifted to a site-wide holistic evaluation model — meaning poor performance on any one page template can now affect your entire domain's search presence.

Key Takeaways

  • LCP measures loading — specifically, when the largest visible content element finishes painting. Good = under 2.5s. It's a waterfall of four phases; diagnose which phase is slow before fixing.
  • INP measures interactivity — the worst interaction latency across the whole session, from input through JS execution to visual paint. Good = under 200ms. Replaced FID in March 2024 because FID was dangerously incomplete.
  • CLS measures visual stability — the accumulated impact of unexpected layout shifts, scored as impact fraction × distance fraction. Good = under 0.1.
  • All three are evaluated at the 75th percentile of real field data — your worst quarter of users define your score.
  • Use web-vitals v4 with attribution mode to get actionable diagnostics — element selectors, phase breakdowns, device segments.
